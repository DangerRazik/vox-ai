# Vox AI frontend

Интерфейс анализа качества звонков на Angular 22.2.1. Заказчик загружает батчи
и читает отчёты; команда Vox AI создаёт заказчиков и стримы, ставит батчи в очередь.
Рабочий режим использует REST API. Отдельный демо-режим с условными данными
сохранён и не вызывает Whisper/LLM.

## Быстрый запуск

Нужны Node.js версии из `package.json` (22.22.3+, 24.15.0+ или 26+)
и соседний backend с `.env`, окружением `.venv-backend` и зависимостями
из `requirements.txt`. Для проверки аудио нужен ffprobe в PATH либо
`VOX_FFPROBE_PATH`. Подготовка описана в [README backend](../backend/README.md).

```text
vox-ai-workspace/
├── frontend/
└── backend/
    ├── .env
    └── .venv-backend/
```

Из папки `frontend`:

```powershell
npm ci
npm start
```

Команда запускает API на `127.0.0.1:8000`, обработчик очереди и frontend
на `127.0.0.1:4200`. Дождитесь `[Запуск] Готово: http://localhost:4200` и откройте
сайт. Логи помечены `[API]`, `[Обработчик]`, `[Фронт]`. Ctrl+C останавливает все три
процесса. БД, материалы и результаты сохраняются между запусками.

Перед общим запуском остановите отдельно запущенные службы. Скрипт проверяет
порты и блокировки обработчика; чужие процессы он не завершает.

```powershell
npm start -- --check
npm start -- --port 4201 --api-port 8001
```

Переопределения: `VOX_BACKEND_DIR` и `VOX_BACKEND_PYTHON` — полные пути;
`VOX_FRONTEND_PORT` и `VOX_API_PORT` — порты по умолчанию.
После изменения Python-кода или backend `.env` перезапустите общий запуск.

## Подключение и работа

В форме входа нужен только API-ключ. Сервер определяет роль и организацию
через `/v1/access-context`. Команда входит по `VOX_ADMIN_API_KEY`, заказчик —
по ключу, выданному при создании организации. Подключение сохраняется
в localStorage браузера; «Выйти» удаляет его. Адрес API пользователь не вводит.

Заказчик выбирает стрим, загружает ZIP с аудиозаписями и проверяет результат
приёма. При необходимости повторяет импорт или восстанавливает тот же батч.
После обработки доступны сводный отчёт, разбор звонка и сравнение.
Поля JSON-метаданных в форме нет; способ передачи метаданных предстоит согласовать.

Команда создаёт заказчика и сохраняет его ключ — он показывается один раз.
Затем создаёт стрим с базой знаний, промптом Whisper и опциями обработки
и ставит готовые батчи в очередь кнопкой «Поставить в очередь».
Стрим сам по себе не запускается: worker последовательно обрабатывает батчи
из общей FIFO-очереди. После восстановления нужен новый ручной запуск.

Новый стрим использует все **11 фиксированных критериев**. Чекбоксы выбора убраны;
конструктор критериев отложен. Создание на основе стрима даёт новый ID и также
использует все 11 критериев. Старые снимки сохраняют свои правила.
Модели, язык и шаблоны ролей/анализа берутся из backend; промпт Whisper
предзаполняется и доступен для изменения.

База знаний — непустой текст UTF-8. При включённых опциях загружаются отдельные
словари: корректировки — JSON-объект «строка → строка», нежелательные выражения —
JSON-массив строк. Формат и содержимое проверяет сервер.

## Текущее поведение экранов

- Название батча берётся из имени ZIP без расширения; ID остаётся отдельным идентификатором.
- Статусы обновляются автоматически; незавершённые результаты не показываются.
- «Средние оценки критериев» — горизонтальный график в отчёте батча без дублирующей
  таблицы. Среднее может быть 0,62, хотя оценка одного звонка принимает 0, 0,5 или 1;
  критерий 5.2 принимает 0 или 1.
- Критические нарушения — количество из числа успешно обработанных звонков.
- В разборе сворачиваются критерии, транскрипция, метрики, проверка базы знаний и
  рекомендации. Браузер запоминает выбор; итог и критическое нарушение всегда видны.
- Сравнение читает готовые отчёты одного стрима. После успешного ответа список
  выбора и кнопка сравнения скрываются, остаётся таблица в порядке выбора.
  Графика и кнопки «Изменить выбор» нет. При ошибке форма доступна для повтора;
  смена стрима или новое открытие страницы возвращают выбор батчей.
- «Нет данных» не подменяется нулём. Права, статусы и оценки определяет backend.

## Отдельный frontend и развёртывание

```powershell
npm run start:frontend
```

Запускается только Angular; API и обработчик нужны отдельно. Другой API задаётся
перед запуском:

```powershell
$env:VOX_API_TARGET = 'http://127.0.0.1:8001'
npm run start:frontend
```

Dev-прокси из `proxy.conf.cjs` направляет `/api/v1` сайта на `/v1` backend.
`npm run build` создаёт статические файлы в `dist/vox-ui`. Для production нужны
сервер раздачи frontend с возвратом `index.html` для маршрутов приложения,
HTTPS и прокси `/api/v1` к API, а API и worker — отдельные постоянные службы.
Dev-прокси в production-сборку не входит.

## Проверки

```powershell
npm run typecheck
npm test
npm run build
npm run test:launcher
npx playwright install chromium
npm run test:e2e
```

Компоненты проверяются Angular TestBed/Vitest, браузерные сценарии — Playwright.
Playwright запускает только frontend. Обычные сценарии используют демо или
контролируемые HTTP-ответы, без Whisper/LLM. Для установленного Chrome и другого
порта задайте `PLAYWRIGHT_CHANNEL=chrome` и `PLAYWRIGHT_PORT` в окружении PowerShell.

Живые сценарии требуют настроенного Python/ffprobe и свободных портов.
Они используют временные БД и файлы, не рабочую БД:

| Файл | Переменная включения | Проверка |
| --- | --- | --- |
| `e2e/rest-live.spec.ts` | `VOX_LIVE_BACKEND=1` | Вход, изоляция организаций, создание стрима |
| `e2e/rest-upload-live.spec.ts` | `VOX_LIVE_UPLOAD=1` | Приём ZIP, повтор и восстановление |
| `e2e/rest-admin-live.spec.ts` | `VOX_LIVE_ADMIN=1` | Административные операции |

Пример без моделей:

```powershell
$env:PLAYWRIGHT_CHANNEL = 'chrome'
$env:VOX_LIVE_BACKEND = '1'
$env:VOX_API_TARGET = 'http://127.0.0.1:8765'
$env:PLAYWRIGHT_PORT = '4201'
npx playwright test e2e/rest-live.spec.ts --workers=1
```

`e2e/rest-reports-live.spec.ts` читает подготовленные опубликованные батчи при
наличии `VOX_REPORTS_FIXTURE` — пути к JSON-файлу с `root`, `database`, `admin_key`,
`customer: {name, api_key}`, `stream_id`, `batch_ids`, `call_ids`.
Подготовка через настоящие Whisper/LLM выполняется отдельно. Сам тест запускает
только API и читает результаты. Файл с ключами храните в игнорируемой
`.scratch/runtime/`. Без настроек живые сценарии пропускаются.

## Структура проекта

| Путь | Назначение |
| --- | --- |
| `src/app/connection/` | Вход, ключ, REST-адаптеры и рабочая оболочка |
| `src/app/batches/`, `src/app/uploads/` | Батчи, состояния, загрузка и восстановление |
| `src/app/streams/`, `src/app/customers/` | Стримы, материалы и административные экраны |
| `src/app/reports/`, `src/app/comparison/` | Отчёты, разбор звонков, график критериев и сравнение |
| `src/app/shared/` | Общие оболочки и форматирование |
| `src/styles.css` | Общие стили |
| `scripts/start-local.mjs`, `scripts/backend-service.py` | Общий локальный запуск |
| `e2e/` | Браузерные сценарии |
