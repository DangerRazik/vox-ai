# Интеграция frontend и backend

> Текущий режим: только REST API. Демонстрационные источники, маршруты и сценарии удалены 12.10.2026. Описания ранних этапов ниже сохранены как история проектирования.

## Выбор критериев (2026-10-09)

Форма передаёт `config.enabled_criteria`: непустой массив уникальных ID из 11 доступных
критериев. По умолчанию выбраны все; отсутствие поля у прежних клиентов также означает все.
Снимок и публичное поле `criteria` содержат выбранный набор. При создании на основе
стрима набор копируется. Результаты, сводки и батчи передают `max_total`; UI использует
его вместо постоянного 11. Отключённые критерии отсутствуют в оценках и средних.
Если 5.2 выключен, проверка критического нарушения и обнуление не выполняются.
Старые стримы и опубликованные результаты не пересчитываются.

Первоначальный план: 2026-10-06. Текущее состояние: №12–15 выполнены,
[приёмка и ревью №13](../.scratch/vox-ai-ui/reviews/13-review.md) завершены. Итоговое ревью №12
завершено. [Актуальный контракт и проверки №12](#реальное-подключение-12--состояние-на-2026-10-08)
описаны ниже; прежние уточнения остаются историей проектирования.

Backend параллельно разрабатывает другой человек. Frontend сначала работает на демонстрационных данных, затем подключается к REST API. Backend меняется только по отдельному разрешению пользователя: контекст ключа в №12 и минимальное ZIP-восстановление в №14. Остальная реализация ведётся отдельно.

2026-10-07 после первоначальной проверки обновлён backend из GitLab до `6de5b1d`. Теперь есть FastAPI, Bearer-авторизация, публичные списки стримов и батчей с серверной изоляцией организаций. Подробная проверка готовности записана в [тикете №12](../.scratch/vox-ai-ui/issues/12-rest-connection-and-batches.md). Для завершения интеграции остаются контекст организации/полномочий по ключу, адрес и доступная среда API, решение по пагинации и полям списка батчей. Живой вход здесь не проверен: REST-окружение backend не перенесено через Git.

Реализованные `GET /v1/streams` и `GET /v1/batches` возвращают `{items: [...]}` без пагинации. Публичный стрим содержит `stream_id`, `customer_id`, `name`, `created_at`, `criteria` с `id`/`title`, модели/язык и `options` с `speech_rate_enabled`, `unwanted_expressions_enabled`, `text_correction_enabled`, `zero_total_on_critical`. Батч содержит `batch_id`, `stream_id`, `customer_id`, `upload_id`, `status`, `total_calls`, даты обработки и `error`, но не название загрузки или средний балл. Эти различия нужно явно учесть при адаптации интерфейса.

`GET /v1/customers/{customer_id}` возвращает название организации, но требует уже известный ID. Операция контекста текущего ключа отсутствует; получение ID из списков не покрывает нового заказчика без данных. В исходном FastAPI нет CORS middleware; доступ браузера можно обеспечить согласованной настройкой CORS или прокси. Модели и worker для проверки подключения и списков не нужны.

## Основа контракта

Основа выбрана пользователем 2026-10-06: наш проект `../backend/docs/rest-api.md`, путь от корня frontend-репозитория. Его используем для моделей и ожидаемого поведения frontend. Не считать перечисленные endpoints уже реализованными. Подтверждение выбора пользователем не заменяет согласование технических дополнений с разработчиком backend.

Опорные правила проекта: Bearer API-ключ, организация определяется сервером, отдельные административные полномочия, JSON с `snake_case`, отсутствующие показатели как `null`, отдельные ошибки загрузки и обработки, публикация результатов после сохранения всего батча. Точные технические форматы и пути должны быть согласованы.

## Подход frontend

Ручной запуск демо №11 реализован через `AdminBatchesSource.start(batchId)`. Будущий адаптер использует предложенный `POST /admin/batches/{batch_id}/start`: первый запуск готового батча — 202 и `queued`; повтор для `queued`/`processing`/`completed` — 200 с текущим состоянием без нового задания; неподготовленный батч — 409, отсутствующий — 404. При потере подтверждения интерфейс сохраняет ID и позволяет повторить тот же запрос. Восстановленный готовый батч ставится в конец очереди новым ручным действием. Фильтр организации задаёт контекст просмотра, не владельца батча.

`AdminBatchesSource.queue()` предоставляет текущий обрабатываемый батч и упорядоченные ожидающие задания всех организаций. Общая FIFO и один активный батч соответствуют бизнес-требованиям. Для REST необходимо согласовать операцию чтения общей очереди, идентификацию владельца и поля порядка/времени принятого запуска; нового согласованного endpoint в этом документе нет. Контракт административного списка/чтения отчётов произвольной организации также требует подтверждения. Сервер определяет полномочия и актуальный порядок, интерфейс не рассчитывает рабочую очередь самостоятельно.

Демонстрационный источник хранит очередь в памяти. Явное действие имитации завершает текущий батч целиком подготовленным набором условных результатов и запускает следующий; оно не имеет рабочего REST-аналога. Статус завершения и полный отчёт публикуются вместе, без промежуточных аналитических результатов (ADR-0003). Отчёт батча, разбор звонка и сравнение читают одну сводку; разбор учитывает опции сохранённого снимка стрима. Удалённые стримы исключаются из ожидающих заданий и последующих шагов обработки. Сценарии ошибок принадлежат только демо-источнику. Полная перезагрузка сбрасывает очередь и новые отчёты.

Запуск и панель очереди доступны только при выбранном демо-режиме команды; источник также проверяет этот режим. Прежние адреса чтения демонстрационных батчей команды остаются доступными как просмотр примеров, без административных действий в режиме заказчика. Эти ограничения не заменяют будущую серверную авторизацию административных чтений и операций.

В демо №10 создание на основе читает административный снимок и вызывает обычный `AdminStreamsSource.create` с новой конфигурацией и заново выбранными файлами. Дополнительный clone-endpoint не вводится. Будущий адаптер использует тот же multipart `POST /admin/customers/{customer_id}/streams`; переиспользование серверных файлов остаётся вопросом контракта. Метаданные не преобразуются в фиктивные `File`.

`AdminStreamsSource.delete` возвращает удаление, запрет занятости или отсутствие ресурса; транспортный сбой сохраняет подтверждение для решения пользователя. Будущий адаптер использует `DELETE /admin/streams/{stream_id}`: 204 — успех, 409 `resource_busy` — активный импорт/обработка, 404 — ресурс недоступен, в том числе повторное удаление. Отсутствие ресурса не отображается как подтверждённый успех каскада. На время запроса действия подтверждения блокируются. После успеха повторные чтения списков/отчётов не должны возвращать удалённую историю; задания очереди также удаляются согласно проекту контракта.

Демонстрационное удаление очищает каталог, загруженные батчи, исходы приёма и прогресс восстановления выбранного стрима; исходные отчёты становятся недоступны через источник. Проверяется занятость по состояниям батчей и незавершённым запросам приёма/восстановления. Это модель поведения в памяти текущего приложения, а не реализация серверного каскада или доказательство авторизации. Полная перезагрузка восстанавливает исходный демонстрационный набор.

- Общая модель данных экранов, отдельный источник демонстрационных данных и отдельный адаптер REST API.
- Явный выбор режима; недоступность рабочего API не включает демо автоматически.
- Согласованные демонстрационные наборы для двух разделов, ошибок и пустых состояний.
- Сохранение API-ключа в браузере между посещениями; «Выйти» удаляет локально сохранённый ключ.
- Сохранение идентификатора исходной загрузки для повторов и восстановления.

Демонстрационный приём ZIP реализован через `UploadsSource.upload`: запрос содержит идентификатор загрузки, выбранный стрим, ZIP и необязательный JSON как файлы. Будущий REST-адаптер преобразует их в multipart `POST /batch-archives` (`upload_id`, `stream_id`, `archive`, `metadata_file`). Организация в модели экрана задаёт контекст демо; рабочий сервер определяет её по ключу. Результат приёма содержит батч, принятые уникальные пути, дубликаты с исходным путём и ошибки отдельных файлов. Точные поля ответа ещё требуется согласовать.

Демо не раскрывает ZIP и не проверяет его пароль или аудиопотоки. Проверка формы не заменяет проверку сервером. Результаты файлов условные и явно помечены. Повтор после потери подтверждения использует сохранённые файлы и тот же ID; результаты и новые батчи хранятся только в памяти до перезагрузки страницы. Настройки сценария принадлежат демонстрационному источнику и не входят в запрос REST.

Сведения о состоянии реализованы через `BatchesSource.batchDetails`, повторная загрузка — через `UploadsSource.restore`. Модель сведений содержит исходный ID загрузки, стрим, причину сбоя и при восстановлении число повторно принятых уникальных записей относительно исходного состава. REST-адаптер должен использовать `GET /batches/{batch_id}` и повторный `POST /batch-archives` с прежними `upload_id`/`stream_id`; `batchId` в модели действия задаёт ожидаемый ресурс, отдельный endpoint восстановления не предлагается.

Первичный импорт с незакрытым составом допускает исправленный архив. Для `batch_failed` проверяется весь исходный набор по содержимому, а не байты ZIP; стрим и состав сохраняются. Прогресс повторного приёма должен относиться к последней неуспешной попытке и не сбрасываться при повторе передачи. Он не означает сохранённый аналитический прогресс: согласно ADR-0003 результаты публикуются только после обработки всего батча. В демо сравнение состава условное, выбранные файлы не анализируются; после обрыва интерфейс перечитывает актуальные сведения без сброса формы. Точные поля ответа о составе/прогрессе и кодах конфликта ещё нужно согласовать с backend.

Публичный каталог готовых стримов реализован через `PublicStreamsSource.readyStreams`. Модель экрана содержит текущую организацию, ID/имя/дату создания стрима, названия 11 критериев и четыре публичные опции: анализ темпа, поиск нежелательных выражений, корректировка текста и обнуление итога при критическом нарушении. Промпты и содержимое/файлы материалов в модель не включены. Демо использует тот же каталог идентификаторов, что и фильтр батчей; все перечисленные демо-стримы готовы. Состояния пустого списка и ошибки — отдельные условные ответы, не изменения стримов.

Будущий адаптер использует предложенный `GET /streams`, контекст организации определяется ключом. Согласовать точные имена публичных полей в `snake_case`, структуру критериев/опций и получение контекста организации; новые endpoints здесь не предлагаются. Выбор стрима в URL задаёт фильтр интерфейса, а не полномочия или владельца данных. Рабочий сервер должен возвращать только готовые стримы доступной организации.

Создание и список заказчиков реализованы через `CustomersSource.create(name)` и `CustomersSource.list()`. Будущий REST-адаптер использует предложенные `POST /admin/customers` с `name` и `GET /admin/customers`. Результат создания содержит организацию и выданный ключ; модель обычного списка содержит только ID и название, без ключа. Точный формат ответов и ошибок нужно согласовать. Реальный ключ доступен только в результате создания; повторную выдачу, замену, отзыв и удаление организации этот экран не предлагает.

Демонстрационные источники заказчиков и батчей используют общий `DemoOrganizations`: новая организация появляется в обоих экранах, но ещё не имеет стримов. Каталог живёт в памяти до перезагрузки; условный ключ `demo-only-` не сохраняется в каталоге, URL или браузерном хранилище. Выбранный демо-раздел сохраняется в `sessionStorage` вкладки и сбрасывается при выходе. Guard административного экрана и проверка демонстрационного источника ограничивают сценарий выбранным режимом команды, а не заменяют серверную авторизацию.

Демо-ошибка создания происходит до изменения каталога, поэтому повтор безопасен в этом сценарии. Для настоящего API требуется согласовать поведение при потере ответа после успешного создания: как установить исход операции и получить выданный ключ без повторного создания заказчика. Механизм идемпотентности создания в текущем проекте контракта не определён и не имитируется этим экраном.

## Что согласовать перед подключением

Административные стримы реализованы через `AdminStreamsSource.list(organizationId)`, `details(organizationId, streamId)` и `create(request)`. Создание соответствует предложенному `POST /admin/customers/{customer_id}/streams`: multipart с JSON `config`, обязательным `knowledge_base` и файлами `unwanted_expressions`/`text_corrections`, когда включены соответствующие опции. Название, оба промпта и четыре опции входят в конфигурацию; набор критериев фиксирован и не редактируется пользователем. Точные имена JSON-полей и схемы ответа нужно согласовать. Полный снимок соответствует `GET /admin/streams/{stream_id}` и содержит метаданные материалов без сервисных секретов; организация в запросе экрана задаёт ожидаемого владельца, сервер проверяет полномочия и принадлежность.

В проекте API административная операция списка стримов выбранного заказчика ещё не определена. Нужно согласовать получение каталога для произвольной организации командой, не предполагая, что публичный `GET /streams` с контекстом по ключу уже обеспечивает этот сценарий. Дополнительный endpoint или параметр здесь не объявляется согласованным.

`DemoStreamCatalog` содержит неизменяемые снимки и используется источниками административного просмотра, публичного каталога и батчей. После создания фиксируются ID, время, промпты, опции, критерии и метаданные файлов; сами файлы в каталоге не хранятся. Публичный источник выдаёт отдельную проекцию без промптов и материалов. Исходные снимки содержат условные примеры, а не реальные настройки сервисов. Данные существуют только до перезагрузки страницы. Форма и демонстрационный источник проверяют обязательность/непустой размер материалов, но не их содержимое; готовность демо не подтверждает пригодность файла для настоящей обработки.

До рабочего подключения согласовать поддерживаемые форматы и проверку материалов, полную схему снимка, ошибки незавершённой конфигурации и получение исхода создания при потере ответа. Демо-сбой происходит до изменения каталога; реальный повтор после серверного создания не должен создавать незапрошенный дополнительный стрим. Идемпотентность создания в текущем проекте контракта не определена. Для создания на основе в демо №10 требуются новые файлы; переиспользование серверных материалов необходимо согласовать при интеграции №15.

Сравнение реализовано через `BatchesSource.compareBatches`: выбранный стрим, контекст организации и упорядоченные ID батчей. Демо повторно использует исходные опубликованные отчёты и полные сводки, опубликованные при имитации очереди; удаляет повторы ID с сохранением первого положения и отклоняет недоступные, незавершённые или относящиеся к другому стриму батчи. Модель результата содержит массив колонок с батчем и его сводкой; LLM не вызывается. Отображение процентов и округление чисел относятся к интерфейсу, расчёт аналитических показателей остаётся у источника.

Будущий адаптер преобразует запрос в предложенный `POST /streams/{stream_id}/comparisons` с `batch_ids`. Организация в модели — контекст экрана, полномочия определяются сервером по ключу. Ответ должен содержать серверные сводки в порядке запроса, с `null` для отсутствующих показателей; точные поля нужно согласовать. Отказы 404/409 и ошибки транспорта отображаются без подстановки демо. Текущие проверки видимости/URL и демонстрационная валидация не подтверждают авторизацию настоящего backend.

- Как сервер возвращает название текущей организации и административные полномочия по API-ключу. В текущем проекте отдельная операция контекста подключения не определена.
- Поля и форматы ответов для стримов, батчей, звонков, отчётов и сравнений; доступность промптов и материалов только в административном разделе.
- Формат ZIP-загрузки и необязательного файла метаданных, правила повторов с прежним идентификатором и получение исхода при обрыве запроса.
- Получение актуальных статусов и публикация отчёта: какие поля доступны до завершения и после него.
- Пагинация, фильтры и формат ошибок.
- Создание заказчика и выдача ключа, создание стрима на основе существующего, постановка батча в очередь и подтверждённое удаление стрима.
- Адрес API для среды разработки и разрешение запросов с адреса frontend.

Этот список фиксирует вопросы интеграции, а не новые бизнес-требования. Согласованные правила обработки звонков не пересматриваются.

## Реальное подключение №12 — состояние на 2026-10-08

Реализованы форма `/connect`, серверный контекст ключа, рабочие каталоги заказчика
`/customer/batches`, `/customer/streams` и чтение для команды в `/team/batches`,
`/team/streams`. Выше сохранены прежние проектные уточнения; этот раздел фиксирует
актуальное решение для №12, остальные операции относятся к №13–15.

- Пользователь разрешил добавить в backend **только** `GET /v1/access-context`:
  `{role:'customer',customer:{customer_id,name}}` либо `{role:'admin',customer:null}`.
  Вход не требует непустых каталогов; роль не выбирается в интерфейсе и не хранится
  в localStorage. Guard восстанавливает её с сервера после перезагрузки.
- Запросы — Bearer, snake_case, `/v1`. В браузере используется `/api/v1` и
  `proxy.conf.cjs`: `/api` снимается, целевой адрес `VOX_API_TARGET` либо
  `http://127.0.0.1:8000`. Это dev-настройка; production-прокси настраивается отдельно.
- `GET /v1/streams?customer_id=...` и `GET /v1/batches?customer_id=...&stream_id=...`
  возвращают `{items:[...]}` целиком. Выбор статуса фильтрует уже полученный полный
  список; пагинация не имитируется. Данные в прежнем выборе сразу очищаются,
  предыдущий запрос отменяется. Заказчик использует только ID из контекста ключа.
- API не возвращает пользовательское имя загрузки/ZIP. В таблице честно показан
  исходный `upload_id` как «Загрузка …»; фиктивное имя файла не создаётся.
  Средние читаются из опубликованных сводок
  `GET /v1/streams/{stream_id}/dashboard`, только для завершённых батчей. `null` —
  «Нет данных», 0 — «0 из 11», остальные статусы — «Ещё не опубликован».
  Недостающий опубликованный отчёт вызывает ошибку чтения, а не выдуманный ноль.
- Общие модели, `BatchesCatalog` и `PublicStreamsSource` используются адаптерами,
  `BatchTable` переиспользуется в обоих режимах. Рабочая оболочка отделена от демо;
  ссылки на ещё не подключённые операции не ведут к условным результатам.
- Сохранён только адрес и ключ одного подключения. Выход/смена удаляет их и контекст;
  401 требует нового ключа, временный сбой сохраняет подключение и предлагает повтор.
  Тайм-аут чтения — 20 секунд. Ключ не включается в URL, сообщения и журналы.
- Подробные REST-отчёты и сравнение — №13; ZIP и восстановление — №14;
  изменения заказчиков/стримов/очереди — №15. Их демо-сценарии остаются доступными
  при явном выборе демонстрации.

Проверки: компоненты формы через DOM + контролируемый HTTP; браузерные сценарии
со сменой ключа, сохранением, выходом, 401/503, каталогами, фильтрами,
нулём/отсутствием оценки, отменой позднего ответа, правами, клавиатурой и узким экраном.
Живая проверка `e2e/rest-live.spec.ts` прошла на отдельном backend с временной БД:
вход двух заказчиков/команды, чтение, обновление страницы и реальные 401/403/404.
Whisper/LLM не вызываются. Backend-контекст покрыт публичным REST-тестом.

## Настоящие отчёты и сравнение №13 — 2026-10-08

Рабочие разделы заказчика и команды открывают `/batches/{batchId}/report` и
`/batches/{batchId}/calls/{callId}` относительно своего раздела. У заказчика также
доступно `/customer/comparison`. Общие экраны, модели отчётов и таблицы используются
в обоих режимах через `ReportsSource`; рабочая оболочка не предлагает демо-сценарии.
Загрузка/восстановление и административные изменения остаются задачами №14/15.

Подтверждённые операции текущего backend:

- `GET /v1/batches/{id}` — статус и метаданные; `GET /v1/streams/{id}` — публичный
  снимок с флагами **внутри `options`**, включая темп и обнуление итога. Команда
  читает название владельца через `GET /v1/customers/{id}`, заказчик — из контекста ключа.
- `GET /v1/batches/{id}/report` — опубликованная сводка: счётчики, средний итог,
  все `criterion_averages`, количество и доля критических нарушений. `null`
  означает отсутствие результатов; опубликованный 0 остаётся нулём.
- `GET /v1/batches/{id}/calls` возвращает только метаданные. Для таблицы звонков
  читаются `GET /v1/calls/{id}/report`, не более пяти одновременно. Порядок
  соответствует списку звонков. Ошибка чтения не подменяет строку результатом
  анализа: весь экран предлагает повтор запроса.
- Подробный ответ содержит `status: successful | processing_error`, `result`
  либо `null`, `error`. Для `call_processing_failed` показывается общая ошибка
  обработки: backend не сообщает этап сбоя. ID звонка, батча и стрима проверяются
  вместе, поэтому другой звонок не показывается под чужим URL батча.
- В `result` отображаются исходные `scores`/`reason`, сохранённый `total`,
  канонический `critical_violation`, причина, `_segments` с OPERATOR/CLIENT,
  `_metrics`, `kb_check` с вопросами и расхождениями, `recommendations`.
  Оценки не пересчитываются. Неприменимость определяется по серверному пояснению,
  без изменения исходного балла. Неизвестная роль явно обозначается; отсутствующие
  необязательные блоки не заполняются примерами. Аудиоплеера нет.
- `POST /v1/streams/{id}/comparisons`, `{batch_ids:[...]}` — сохранённые сводки
  одного стрима в порядке выбора. Повторы исключаются с сохранением первого
  положения. Сравнение не запускает новый анализ. Серверные 409 объясняют разные
  стримы или отсутствие публикации, 403/404 — недоступность данных, 422 —
  некорректный выбор. Временный сбой допускает повтор с прежним выбором.

До завершения батча и при `409 report_not_available` отчёт недоступен. 403/404
не раскрывают содержимое; 401 очищает подключение и возвращает к вводу ключа.
Смена выбора/выход отменяют незавершённые запросы. Автоматической подстановки
демо-данных нет. Реализация backend в №13 не изменялась.

Живая приёмка использует два отдельно подготовленных маленьких батча одного
стрима с настоящими Whisper/LLM, затем читает сохранённые результаты через API.
`e2e/rest-reports-live.spec.ts` запускает только API, не worker; адреса моделей
недоступны и их ключи заменены тестовыми. Переключение, отчёт, разбор,
перезагрузка, сравнение и узкий экран проверяются без повторного анализа.

## REST-загрузка и восстановление №14

Рабочий заказчик открывает /customer/upload из списка батчей. POST /batch-archives
передаёт multipart upload_id, stream_id, archive и необязательный metadata_file;
customer_id определяется ключом. Частичные исходы файлов отображаются раздельно.
Нет лимита размера или числа файлов, короткий таймаут обычных API-запросов
не применяется к передаче ZIP. При выходе незавершённые запросы отменяются.

ID и выбранный стрим сохраняются до запроса в localStorage, отдельно для адреса
API и организации. Файлы остаются в памяти браузера; после reload их выбирают
заново. При reload или неопределённом ответе читается GET /batches с customer_id
и stream_id, затем /batches/{id}/files. При ошибке этого чтения повторная отправка
и новая загрузка блокируются до проверки фактического состояния. Новая независимая
загрузка явно создаёт новый UUID. Подтверждённый готовый батч не отправляется
повторно автоматически, ошибки REST не подменяются демонстрацией.

/customer/batches/{id}/state и /team/batches/{id}/state показывают серверное
состояние, ID и исходы файлов. Заказчик может повторить начальный импорт или
восстановить исходный полный набор в тот же батч/стрим/upload_id; команда здесь
только читает состояние. Прогресс восстановления не придумывается: текущий
backend не публикует количество restoration_receipts. Конфликты показаны явно,
формы сохраняют файлы и допускают исправление. Для частичного первичного импорта
сохраняются пути и метаданные манифеста; восстановление общего сбоя допускает
переименование и опущенные метаданные. Только ready означает готовность
к ручному запуску. Автоматический запуск и вызовы моделей отсутствуют.

Минимальное исправление backend отдельно разрешено пользователем:
[разрыв и решение](../.scratch/vox-ai-ui/backend-zip-recovery-gap.md).
Аварийное завершение процесса API может оставить active_uploads — это известное
ограничение backend, отличное от потери ответа браузером; интерфейс показывает
upload_in_progress, не создавая второй батч. Административные REST-операции — №15.

Проверки: e2e/rest-upload.spec.ts, компонент rest-upload-page.spec.ts и существующие
формы; opt-in e2e/rest-upload-live.spec.ts. Живой стенд создаёт временную БД,
использует call_002.mp3 и ffprobe, намеренно отсутствующий материал стрима для
общего сбоя перед моделями и затем восстанавливает ZIP через браузер. Адреса
моделей недоступны, ключи тестовые; данные и процессы стенда удаляются.

Приёмка и ревью №14 завершены: [результаты](../.scratch/vox-ai-ui/reviews/14-review.md).

## Административные REST-операции №15 — 2026-10-08

Рабочие `/team/customers` и `/team/streams` используют те же формы и снимки,
что и явно обозначенное демо, с отдельными REST-источниками. Маршруты проверяют
роль из `/v1/access-context`; разрешение операции всегда проверяет backend.
При 401 подключение сбрасывается; 403 показывается как отказ прав.

- `GET/POST /v1/admin/customers`: создание показывает `api_key` только в квитанции;
  после закрытия/перезагрузки список не содержит ключей. Копирование ключа имеет
  прежний ручной вариант при недоступном Clipboard API.
- `GET /v1/streams?customer_id=…` и `GET /v1/admin/streams/{id}`: полный снимок
  текущей организации. API отдаёт размер и SHA-256 материалов, без исходных имён
  и MIME; интерфейс показывает назначение материала и отсутствие типа. Сервисные
  ключи и пути хранения не входят в отображаемую модель.
- `GET /v1/admin/stream-defaults`: исходный `whisper_prompt` для новой формы.
  При отказе форма скрыта, доступен повтор чтения; демонстрация не подставляется.
- `POST /v1/admin/customers/{id}/streams`: multipart `config`, `knowledge_base`,
  `unwanted_expressions`, `text_corrections`. С 2026-10-08 сайт отправляет имя,
  редактируемый Whisper-промпт, два порога и четыре опции. Модели, язык,
  промпт ролей и два LLM-промпта скрыты в форме и просмотре; backend берёт
  отсутствующие поля из `config.py`, `transcriber.py`, `analyzer.py` и фиксирует
  полный снимок. Скрытые значения не дублируются константами frontend.
  Полные конфигурации прежних API-клиентов совместимы. Форма сохраняет
  поля/файлы при исправляемом отказе; материалы валидирует сервер.
- База знаний — непустой текст UTF-8; корректировки — непустой JSON-объект
  строка → строка; нежелательные выражения — непустой JSON-массив строк.
  Включённая словарная опция требует файл. Выключенные словари не передаются.
- «Создать на основе стрима» переносит Whisper-промпт, пороги и опции в новую форму.
  Скрытые настройки нового стрима берутся из текущего кода backend. Согласованный
  действующий контракт не имеет скачивания/копирования материалов: их выбирают
  заново, затем обычный POST создаёт новый ID. Старый снимок и история сохраняются.
- `POST /v1/admin/batches/{id}/start`: 202 — новая постановка, 200 — текущее состояние
  при повторе, 409 — запуск отклонён. После ответа читается фактический батч с
  организацией/стримом. При потере подтверждения повторяют **тот же batch_id**.
  `StartBatchesSource` содержит только запуск; широкое `AdminBatchesSource.queue()`
  остаётся демонстрационным. API не отдаёт порядок/позицию общей FIFO — интерфейс
  показывает серверный статус, не рассчитывает порядок из даты загрузки.
- `DELETE /v1/admin/streams/{id}` выполняется только после отдельного подтверждения
  необратимого удаления батчей, транскрипций и истории. 204 очищает снимок;
  409 `resource_busy` сохраняет его и подтверждение. По текущему backend занят
  ресурс с active_uploads либо статусом uploading/restoring/processing или занятым
  файловым lock. Ожидающее queued-задание удаляется вместе со стримом.
- Отчёты команды из №13 сохраняют реальную организацию и стрим; выбор организации
  задаёт контекст просмотра, но не заменяет серверную авторизацию.

Создание заказчика/стрима не имеет ключа идемпотентности. При сетевом сбое
интерфейс предупреждает: сначала обновить список, поскольку создание могло
состояться. Автоматических повторов нет. При потере ответа создания заказчика
получить его ключ повторно нельзя; ротации ключей в текущем API нет.

Живая приёмка: `VOX_LIVE_ADMIN=1`, `VOX_API_TARGET=http://127.0.0.1:8775`,
`PLAYWRIGHT_PORT=4215`, `PLAYWRIGHT_CHANNEL=chrome`, затем
`npx playwright test e2e/rest-admin-live.spec.ts --workers=1`.
Стенд создаёт временные БД/материалы/входы и тестовые ключи, использует настоящее
аудио/ffprobe для загрузки, затем проверяет создание/копирование/ручной старт,
повтор, busy-отказ, каскадное удаление и все административные 403 для заказчика.
Worker и модели не запускаются; URI моделей недоступны. После проверки процесс
API остановлен, временный каталог удалён. В рамках №15 backend-код не изменялся; автоподстановка 2026-10-08 добавлена
отдельным последующим изменением по разрешению пользователя.

Приёмка и независимое ревью №15 завершены: Standards — 0, Spec — 0.
[Подробные результаты](../.scratch/vox-ai-ui/reviews/15-review.md).

Решение об исходных настройках: [ADR 0004 backend](../../backend/docs/adr/0004-stream-creation-source-defaults.md).
Backend после обновления нужно перезапустить: текущий запуск Uvicorn без `--reload`
не подхватит новый маршрут и заполнение параметров. Frontend в режиме `npm start`
обновляется автоматически.

Уточнение действий ZIP-формы 2026-10-08: до первой отправки сброс скрыт.
После закрытого приёма доступно «Загрузить ещё ZIP»: новый ID, пустые файлы,
прежний выбранный стрим. Для известного незавершённого приёма остаётся
«Начать новую загрузку»; при неизвестном исходе сначала проверяют состояние,
а повтор выполняется с прежним ID. Передача архива блокирует смену загрузки.

## Вход только по ключу — 2026-10-08

По запросу пользователя поле «Адрес API» и его подсказки удалены из формы.
`ApiConnection.connect(key)` использует единственный адрес сайта `/api/v1`.
Раздел и организация по-прежнему определяются `GET /v1/access-context`.
Для разработки `proxy.conf.cjs` направляет запросы на `VOX_API_TARGET`
или `http://127.0.0.1:8000`; production размещает аналогичный серверный прокси.
Адрес провайдера задаёт развёртывание, а не заказчик или пользователь команды.

Сохранённое подключение к текущему API восстанавливается; запись с другим
адресом требует ввода ключа заново и не отправляет прежний ключ по старому адресу.
Ошибка связи предлагает повторить запрос, без указаний менять адрес в форме.
Ключ хранится прежним способом и удаляется при выходе/смене подключения.
Восстановление загрузочных черновиков текущего `/api/v1` сохраняет свой ID.

## Автоматическое обновление батчей — 2026-10-08

Черновики ZIP-загрузок теперь сохраняются отдельно по `upload_id`, адресу API
и заказчику. Текущая форма включает `upload` в URL: обновление этой страницы
восстанавливает только её черновик и проверяет исход отправки.
Переход «Загрузить ZIP» из списка без параметра `upload` всегда создаёт чистую
форму с новым ID. «Восстановить» в строке батча использует состояние этого батча
и его прежний ID загрузки, независимо от других черновиков. Старый общий черновик
больше не подхватывается при создании; ранее созданные батчи доступны в списке.

В рабочем каталоге нет кнопки «Обновить список». После первоначального чтения
`WorkspacePage` каждые 10 секунд повторяет чтение списка выбранного стрима
и его опубликованных сводок через `RestBatchesCatalog`. Фильтры сохраняются,
таблица остаётся видимой во время запроса. Медленный запрос не запускает
параллельный опрос, скрытая вкладка пропускает обновления. Смена заказчика,
стрима и уход со страницы отменяют прежний запрос/таймер. При отказе API
показывается ошибка с явным повтором. Чтение не ставит батчи в очередь
и не вызывает модели; сервер остаётся источником статусов и оценок.

## Понятные показатели отчёта — 2026-10-09

Интерфейс отображает `critical_violation_count` из `successful_calls`, например
«1 из 4», без процентов; при нуле успешных звонков — «Нет данных». Контракт
по-прежнему содержит `critical_violation_rate`, но UI не использует его для показа.
Средние критериев отображаются как опубликовано backend: среднее оценок успешных

## Общий локальный запуск — 2026-10-09

По уточнению пользователя 2026-10-09 UI не предлагает файл JSON-метаданных ни
при загрузке, ни при восстановлении. Форма не отправляет `metadata_file`.
Новый способ передачи сотрудника/даты ещё не определён. Backend сохраняет
совместимость существующего API метаданных для внешних интеграций.
Ответы батча содержат `name` (имя исходного ZIP без расширения) и `archive_name`.
`batchFromRest` использует эти данные для списка, состояния, отчёта и сравнения;
при отсутствии имени оставляет «Загрузка <полный upload_id>».

`npm start` из frontend запускает существующие API, обработчик и Angular через
`scripts/start-local.mjs`. Python берётся из соседнего backend/.venv-backend;
API/worker работают с cwd backend, его `.env` и постоянными путями данных.
Настройки можно переопределить переменными окружения, как при отдельном запуске.
Предварительная проверка использует `BackendSettings` и исходный `config.settings`,
проверяет ffprobe и эксклюзивные worker/database locks без запуска анализа.
Сообщения валидации перечисляют поля, не значения ключей.

Проверяются свободные порты API/фронта; занятый процесс не переиспользуется
и не завершается. Запуск ждёт ответа API, затем поднимает worker и фронт.
Прокси Angular направляется на API этого запуска. Ctrl+C и отказ службы
останавливают только дочерние процессы текущего запуска. Python получает
запрос остановки через stdin, включая Windows; после ожидания применяется
завершение собственных процессов и дерева dev-сервера.

`npm run start:frontend` сохраняет отдельный Angular dev server и настройку
`VOX_API_TARGET`. Playwright использует именно эту команду, чтобы его
демо/контролируемые сценарии не запускали постоянную очередь и модели.
`npm run test:launcher` проверяет реальные процессы с временной SQLite,
файлами и фиктивными ключами, без обращения к Whisper/LLM.
