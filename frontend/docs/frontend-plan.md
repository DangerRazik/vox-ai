## Согласованная основа

Выполнен также [тикет №07](../.scratch/vox-ai-ui/issues/07-batch-comparison.md): выбор нескольких завершённых батчей одного стрима, таблица всех показателей в порядке выбора, переход из отчёта, состояния и проверки. Сравнение использует опубликованные сводки; повторного анализа нет.

Выполнен [тикет №08](../.scratch/vox-ai-ui/issues/08-admin-customers.md): список и создание заказчика, выдача и копирование условного ключа только в результате создания, ошибки с сохранением ввода, ограничение операции выбранным демо-режимом команды. Новая организация доступна в общем каталоге и фильтре батчей до перезагрузки страницы. Ключ не используется для авторизации; настоящий REST и серверные полномочия подключаются позднее.

2026-10-07 выполнен [тикет №09](../.scratch/vox-ai-ui/issues/09-admin-stream-creation.md): административный список стримов выбранного заказчика, форма с тремя этапами и условными словарями, обязательная база знаний, фиксированные критерии, новый ID и неизменяемый просмотр. Общий каталог согласует настройки с публичным экраном и фильтром батчей. Форма и источник проверяют полноту файлов; проверка содержимого остаётся у будущего backend. Копирование и удаление стрима относятся к №10, ручной запуск — к №11.

2026-10-07 выполнен [тикет №11](../.scratch/vox-ai-ui/issues/11-admin-batch-queue.md): ручная постановка готового и восстановленного батча, общая FIFO-очередь всех организаций с одним активным заданием, явная имитация последовательного завершения и публикации целого отчёта, безопасные повторы и запрет неподготовленных состояний. У заказчика административные действия отсутствуют. Все 11 задач демо-этапа завершены; REST-задачи №12–15 требуют согласованного контракта и готовых операций backend.

- Отдельный репозиторий `frontend`, последняя стабильная Angular.
- Спокойный светлый интерфейс по предоставленным референсам: белые поверхности, синий акцент, компактные таблицы, адаптация к узкому экрану.
- Два раздела: заказчик и команда Vox AI.
- API-ключ запоминается браузером между посещениями; «Выйти» удаляет локальный ключ. Учётных записей нет.
- Сначала демонстрационный режим, затем REST API. Backend параллельно разрабатывает другой человек.
- Основа интеграции — наш подготовленный проект REST API. См. [план интеграции](integration.md).

| Команда Vox AI | Стримы                        | Просмотр полного снимка, создание нового, создание на основе существующего, удаление с подтверждением.            |

Структура формы нового стрима предлагается как одна страница с тремя последовательными разделами:

1. Whisper: промпт.
2. Обработка транскрипции: три опции и необходимые при включении словари.
3. LLM: промпт, база знаний, правило обнуления итога при критическом нарушении, включённое по умолчанию.

В форме также выбирается заказчик и задаётся имя. Набор из 11 критериев фиксирован. Копирование настроек не меняет исходный стрим. Повторное использование уже загруженных файлов при копировании нужно согласовать с backend: простого просмотра метаданных материалов недостаточно для повторного multipart-приёма файлов.

В демо №10 создание на основе использует эту же форму с известными настройками и требует файлы заново. Удаление выполняется из просмотра после отдельного модального подтверждения имени, ID и последствий; отмена и ошибка сохраняют историю. Демонстрационный источник удаляет выбранный стрим и связанные данные из всех чтений, проверяя активный импорт/обработку; остальные стримы не меняются. Браузерные проверки дополняются публичными проверками предзаполненной формы и компонента подтверждения. Настоящие операции подключаются в №15.

## Предлагаемая техническая организация

- Приложение с отдельными страницами и общими компонентами меню, заголовка, таблицы, статуса, показателя, формы и подтверждения.
- Централизованные стили с согласованными цветами, типографикой, отступами и состояниями компонентов.
- Отдельные модели API и преобразование к данным экранов. Идентификаторы, статусы, имена полей и числовая семантика следуют проекту REST API.
- Демонстрационный источник реализует те же операции чтения и действий, что и будущий REST-адаптер. Экран не зависит от способа получения данных.
- Режимы выбираются явно. В демо используются условные данные и локальная имитация действий; загрузка ZIP не вызывает обработку звонков.
- Для рабочего режима адрес API задаётся конфигурацией. Ключ сохраняется в браузере для этого подключения; при выходе или смене подключения данные экранов очищаются.
- В демо можно выбрать пример роли для просмотра; в рабочем режиме полномочия определяет сервер. Ответ, возвращающий организацию и полномочия, ещё нужно согласовать.
- Точные версии Angular и инструментов проверяются перед установкой и фиксируются в зависимостях и lock-файле. Исходный код backend не изменяется.

## Демонстрационные сценарии

1. Готовый батч ожидает ручного запуска; заказчик не видит кнопку запуска.
2. Команда ставит готовый батч в очередь; повторное действие не создаёт второе задание.
3. Частичный приём ZIP: принятые записи, дубликаты и отдельные ошибки загрузки.
4. Завершённый батч с успешными и неуспешными записями; сводка соответствует деталям звонков.
5. Завершённый батч без успешных результатов: «Нет данных» вместо нулевых средних.
6. Критическое нарушение с включённым правилом: итог 0, исходные оценки сохранены.
7. Критическое нарушение с выключенным правилом: итог — сумма, факт нарушения виден.
8. Неприменимый критерий и отключённый темп: оценка 1 с объяснением.
9. Ошибка всего батча и восстановление с прежним идентификатором; затем ожидание ручного запуска.
10. Сравнение нескольких завершённых батчей одного стрима.
11. Создание стрима на основе существующего и отдельное подтверждение удаления с описанием последствий.
12. Пустые списки, ошибка запроса и повтор, длинная транскрипция, отсутствующие метаданные.

Референсные цифры не требуют буквального переноса: демонстрационный набор должен давать согласованные между собой результаты. Статусы загрузки, ошибки отдельной записи и ошибки всего батча различаются.

## Порядок реализации

1. Инициализация Angular, запуск приложения, каркас и общие компоненты.
2. Модели и демонстрационный источник данных, подключение и два раздела.
3. Все сценарии заказчика: батчи, загрузка, статусы, отчёты, стримы и сравнение.
4. Административные сценарии: заказчики, создание стримов, очередь, отчёты и удаление.
5. Проверка адаптивности, клавиатурной навигации, состояний и согласованности демонстрационных данных.
6. Подключение REST API по согласованному контракту, когда соответствующие операции backend станут доступны.

После каждого этапа результат должен запускаться локально. Перед передачей первой версии проверяются сборка, переходы и основные пользовательские сценарии. Существенные автоматические проверки охватывают границы ролей, состояния публикации отчёта, восстановление и сохранение исходных оценок при обнулении итога.

В ответ на вопрос `to-spec` пользователь дополнительно запросил отдельные проверки компонентов. Проверять формы ZIP и стрима (обязательность полей и условных словарей, ошибки, сохранение ввода), а также блок оценок (исходные баллы, обнуление итога, отсутствие показателей и пояснения). Эти проверки дополняют браузерные сценарии и не зависят от приватных методов компонентов.

## Граница первой версии

Реализуем согласованные экраны и демонстрационные действия. Выгрузку CSV/XLSX/PDF, пользовательские учётные записи, обратную связь сотруднику, редактирование существующего стрима, отзыв ключей и обработку аудио на frontend не добавляем.

Бизнес-процесс и внутренние алгоритмы стрима следуют требованиям backend; повторного проектирования обработки звонков здесь нет.
