**What to build:** Заказчик узнаёт состояние незавершённого батча и восстанавливает общую ошибку повторной исходной загрузкой.

**Blocked by:** 04: Демонстрационная загрузка ZIP.

**Этап:** Демонстрационная первая версия.

**User Stories:** 15, 18–21, 67–69.

- [x] Из списка открываются сведения о uploading, ready, queued, processing, upload_failed и batch_failed; состояния и причины различимы текстом.
- [x] Первичный сбой импорта и общая ошибка обработки имеют разные пояснения и соответствующие действия повторной загрузки.
- [x] Для batch_failed восстановление сохраняет идентификатор загрузки, стрим и полный исходный набор уникальных записей.
- [x] Неполный или изменённый состав не выдаётся за восстановленный; успешное восстановление возвращает тот же батч в ожидание ручного запуска.
- [x] Повтор одной восстановительной передачи не создаёт другой батч и не сбрасывает уже принятый восстановительный прогресс.
- [x] Ошибка отдельной записи в завершённом батче не предлагает перезапуск одной записи.

- [x] Все действия явно выполняются в демо, без реальной обработки аудио.

Проверки входят в эту задачу; реализация backend и изменение бизнес-правил не входят.

## Реализация и проверка

Из списка открывается состояние незавершённого батча: «Статус» для загрузки/готовности/очереди/обработки, «Восстановить» для ошибок импорта и обработки всего батча. `BatchesSource.batchDetails` возвращает исходный ID загрузки, организацию, стрим, входные счётчики, причину сбоя и прогресс повторного приёма. До завершения батча оценки и отчёт не публикуются. Чужой или отсутствующий ресурс не раскрывает сведения; известный контекст и возврат сохраняются при ошибке чтения. Команда может читать сведения, клиентская форма восстановления находится в разделе заказчика.

`RecoveryForm` использует проверенную форму ZIP с фиксированным стримом; ID загрузки и батча берутся из исходных сведений. `UploadsSource.restore` повторяет приём в тот же ресурс. Для `upload_failed` состав ещё не закрыт: допускается исправленный архив с прежним ID. Для `batch_failed` требуются все исходные уникальные записи по содержимому; повторная упаковка ZIP допустима. Сценарии демо явно условные: выбранный архив не раскрывается, его содержимое/пароль не проверяются, файлы не отправляются.

Демо «Батч 03.10»: полный набор — 120 записей и тот же батч в `ready`; неполный — 119 из 120 и конфликт; изменённый — неизвестная запись, конфликт и сохранение исходного состава. Прогресс повторного приёма хранится как набор уникальных условных записей, повтор не увеличивает счётчик и не сбрасывает уже принятые входы. Обрыв сохраняет 60 из 120; повтор того же запроса завершает приём до 120. После сбоя интерфейс перечитывает сведения без пересоздания формы; ошибка этого чтения объясняется отдельно. Это загрузочный прогресс, а не сохранённые аналитические результаты, согласно ADR-0003.

Демо «Исходящие 05.10»: повторная ошибка распаковки оставляет `upload_failed`; исправленный импорт принимает две условные записи в тот же батч и возвращает `ready`. Пример нулевого приёма, созданный через №04, также сохраняет свой исходный ID при повторе. После успеха нужен ручной запуск команды; автоматическая обработка, клиентская кнопка запуска и перезапуск отдельной ошибочной записи завершённого батча не добавлены.

Добавлены **12 браузерных сценариев** и **4 проверки компонента восстановления**. Проверены различные состояния/причины, фиксированный стрим, обязательный ZIP, сохранение исправляемого ввода, конфликты состава, прерванная передача и повтор, первичный импорт, ID динамического батча, доступ разных разделов, ошибка чтения и возврат, отсутствие перезапуска одной записи, узкий экран 390 px и выбор файла с клавиатуры.
