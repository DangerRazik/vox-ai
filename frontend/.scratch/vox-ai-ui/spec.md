## Problem Statement

Заказчику нужен рабочий интерфейс для загрузки звонков, наблюдения за обработкой и изучения качества работы сотрудников. Сейчас frontend отсутствует: требования к анализу и проект REST API уже подготовлены, но пользователь не может пройти сценарии через приложение.

Команде Vox AI нужен отдельный административный раздел для создания заказчиков, настройки стримов и ручного запуска батчей. Заказчик не должен получать административные действия или доступ к данным другой организации.

Backend параллельно разрабатывает другой человек. Поэтому frontend нужно развивать независимо, сначала на согласованных демонстрационных данных, сохраняя возможность подключить общий REST API. Пользователь предоставил визуальные референсы, которые задают направление, но не заменяют требования проекта.

## Solution

Создать frontend на последней стабильной Angular в отдельном frontend-репозитории. Первая поставка — запускаемое локально приложение с явно обозначенным демонстрационным режимом, двумя разделами и всеми согласованными основными экранами. Следующий этап — подключение реального backend по нашему подготовленному проекту REST API, выбранному пользователем как основа.

Заказчик начинает со страницы батчей, выбирает готовый стрим, загружает ZIP и видит исходы приёма. После ручного запуска командой Vox AI и завершения обработки он изучает сводный отчёт, отдельные звонки и сравнивает завершённые батчи одного стрима.

Команда Vox AI создаёт заказчиков и выдаёт ключи при создании, создаёт неизменяемые стримы, ставит готовые батчи в очередь и просматривает отчёты всех организаций. Изменение стрима выполняется созданием нового на основе существующего. Удаление стрима требует отдельного подтверждения с объяснением удаления его истории.

Интерфейс светлый: белые поверхности, тёмный текст, синий акцент, красный для ошибок и критических нарушений, компактные таблицы, умеренные скругления. На узких экранах меню перестраивается, колонки разбора идут последовательно, широкие таблицы остаются доступными через прокрутку.

Пользовательских учётных записей нет. В рабочем режиме API-ключ запоминается браузером между посещениями; «Выйти» удаляет локальный ключ. Демо показывает условные данные и действия; рабочий режим не подменяет недоступность API демонстрационными отчётами.

## Implementation Decisions

- Реализуется отдельное Angular-приложение. Backend развивается другим человеком; его исходный код в рамках этой спецификации не изменяется.
- Выбирается последняя стабильная Angular на момент инициализации, без preview-версии. Точные версии инструментов фиксируются в зависимостях и lock-файле; установка в рамках подготовки спецификации не выполняется.
- Приложение включает страницы подключения, батчей, загрузки, состояния и восстановления, отчёта батча, разбора звонка, стримов и сравнения, а также административные страницы заказчиков, батчей и стримов.
- Общие компоненты обеспечивают единообразные меню, заголовки, таблицы, статусы, показатели, поля, пояснения и подтверждения. Цвета, типографика и отступы централизованы.
- Главное меню заказчика содержит только «Батчи», «Стримы», «Сравнение». Отчёты открываются из батча и звонка, административные действия доступны команде.
- Предложенная компоновка формы создания стрима — одна страница с тремя последовательными разделами этапов. Она не вводит новых бизнес-настроек и может уточняться при реализации в рамках принятого визуального направления.
- Отдельные модули отвечают за контекст подключения, источники данных, преобразование ответов, экраны заказчика, административные сценарии и общие компоненты. Это предлагаемые технические границы, а не уже существующие модули.
- Один интерфейс источника данных обслуживает демонстрационные сценарии и будущий REST-адаптер. Представление экранов не привязывается напрямую к условным наборам.
- Демонстрационный режим выбран явно и постоянно обозначен. Он использует согласованные условные данные и локально имитирует действия; выбранные пользователем файлы не выдаются за реально проанализированные.
- Первая поставка не требует работающего backend. Переключение на реальный источник выполняется отдельным этапом по доступным операциям API; сетевой сбой не включает демо автоматически.
- В демо доступны два примера разделов без настоящих ключей. В рабочем режиме API-ключ определяет права сервером; переключатель интерфейса не предоставляет полномочия.
- Рабочий ключ сохраняется в браузере между посещениями для соответствующего адреса API. Выход удаляет локально сохранённый ключ и контекст. При смене ключа данные прежней организации очищаются. Отзыв ключа на сервере не выполняется.
- В качестве основы API выбран существующий проект: префикс /v1, Bearer-ключ, JSON в snake_case, идентификаторы ресурсов UUID, даты ISO 8601, отсутствие показателя как null. Технические уточнения остаются вопросами интеграции.
- Заказчик выбирает только свои готовые стримы, видит публичные сведения и не редактирует настройки. Административный раздел работает с полными снимками и материалами без сервисных секретов.
- Машинные статусы батча: uploading, ready, queued, processing, completed, upload_failed, batch_failed. Разные уровни ошибок не сводятся к одному состоянию.
- ZIP принимается без пароля. Необязательные метаданные по проекту API задаются отдельным JSON по относительным путям записей; ID сотрудника и дата не обязательны. Дополнительные продуктовые лимиты по числу файлов, размеру или длительности не вводятся.
- Идентификатор загрузки создаётся для новой загрузки и сохраняется при повторе. Новая независимая загрузка получает новый идентификатор. Одинаковое содержимое внутри одного батча соответствует одной записи и не увеличивает ошибки загрузки.
- После завершения загрузки состав батча фиксирован. Восстановление общей ошибки использует прежний идентификатор, тот же стрим и весь исходный набор уникальных записей, затем ожидает ручного запуска. Ошибка отдельного звонка не даёт операции перезапуска одной записи.
- Заказчик не запускает обработку. Команда ставит готовый батч в общую FIFO-очередь; повтор запроса не создаёт ещё одно задание. В демо соответствующие переходы имитируются локально.
- Отчёты появляются после завершения обработки и успешного сохранения полного результата батча. До этого аналитические итоги не отображаются.
- Набор критериев фиксирован: 1.1 «Приветствие», 1.2 «Прощание», 2.1 «Наличие слов вежливости», 2.2 «Темп разговора», 2.3 «Тон разговора», 2.4 «Грамотность и культура речи», 3.1 «Активная позиция и демонстрация внимания», 3.2 «Работа с конфликтом», 4.1 «Постановка/снятие удержания», 5.1 «Соблюдение скрипта и регламента», 5.2 «Критическое нарушение».
- Оценки критериев — 0, 0,5 или 1; 5.2 — только 0 или 1. Неприменимость и выключенный анализ темпа отображаются как 1 с явным пояснением.
- Критическое нарушение канонически определяется оценкой 5.2 = 0. Факт виден независимо от настройки. При включённом правиле обнуляется итог звонка, исходные оценки всех критериев сохраняются. Правило включено по умолчанию при создании стрима.
- Итог показывается как «X из 11», исходные оценки критериев — из 1. Расчёт рабочего результата принадлежит backend; frontend не изменяет опубликованные оценки.
- Сводка включает средний итог успешных звонков, число принятых и успешных записей, отдельные ошибки загрузки и обработки, средние исходные оценки всех критериев, критические нарушения как «1 из 4» по успешным звонкам, без процентов.
- При отсутствии успешных записей средние и показатель нарушений — «Нет данных», в данных число критических нарушений — 0. Батч при этом может быть завершённым; ошибки и счётчики остаются доступны.
- В названиях загрузок и выборе стрима UUID показываются полностью. API, URL, восстановление и БД используют полные идентификаторы.
- Среднее по критерию может быть дробным: это сумма индивидуальных оценок, делённая на число успешных звонков. Шкала отдельного звонка остаётся 0, 0,5, 1.
- Разбор содержит метаданные, итог, все критерии и пояснения, транскрипцию с началом и окончанием реплик и ролями, метрики, проверку по базе знаний и рекомендации. Необязательные отсутствующие данные не заменяются выдуманными значениями.
- Сравниваются несколько завершённых батчей только одного стрима: колонки — батчи, строки — итог, счётчики, ошибки, нарушения и средние всех критериев. Скриншот с двумя батчами не ограничивает число колонок двумя.
- Любое изменение параметров или материалов стрима создаёт новый ID. Предыдущая история сохраняется, пока стрим явно не удалён. Удаление требует отдельного подтверждения и удаляет связанные батчи и историю.
- Рабочие отчёты не зависят от постоянной доступности аудио: после успешного завершения батча входные файлы удаляются, транскрипция сохраняется. Постоянный аудиоплеер в отчёте не нужен.
- Окна выбора и подтверждения ждут действия пользователя. Клавиатурная навигация, видимый фокус, подписи, текстовые статусы и адаптивность входят в требования качества.
- Детали контекста подключения, полные схемы ответов, восстановление после обрыва запроса, переиспользование материалов при копировании стрима, пагинация и настройки среды требуют согласования с разработчиком backend. Они не подменяются неоговорёнными endpoints.

## Testing Decisions

- Основная граница проверки — приложение в браузере: видимый результат пользовательского сценария от действия до состояния экрана. Проверять внешнее поведение, доступность действий и значения, а не внутреннее устройство компонентов.
- Дополнительно пользователь запросил отдельные проверки компонентов. Выбор подтверждён 2026-10-06 в ответ на вопрос о границах проверок.
- В frontend пока нет приложения, тестового раннера или существующих тестов. Поэтому готовой аналогичной инфраструктуры здесь нет; инструменты выбираются при инициализации.
- Сценарные проверки используют демонстрационный источник, без обращений к Whisper, LLM и настоящему backend. При следующем этапе интеграционные проверки охватывают REST-адаптер по согласованному контракту.
- Отдельные проверки компонентов сосредоточены на формах и представлении отчёта: форма ZIP и результаты приёма; форма стрима с условно обязательными словарями; блок исходных оценок и итогового результата.
- Формы проверяются через ввод и действия: обязательность выбранного стрима и ZIP, необязательность метаданных, понятные ошибки и сохранение введённых значений. Включение опции делает соответствующий словарь обязательным; выключение снимает это условие.
- Компоненты отчёта проверяются на данных с нулевым итогом, отсутствием показателей, критическим нарушением с включённым и выключенным правилом, неприменимостью и отключённым темпом. Проверяются видимые значения, пояснения и раскрытие с клавиатуры.
- Проверки не привязываются к приватным методам, дереву внутренних компонентов или вызовам вспомогательных функций. Не нужны отдельные тесты каждой иконки и CSS-класса, если они не проверяют существенное поведение.
- Браузерные сценарии охватывают заказчика и команду, подключение и выход, загрузку и восстановление, статусы, отчёты, сравнение, создание и удаление стрима. Видимость кнопок не считается доказательством серверной авторизации: при подключении API проверяется и серверный отказ.
- Демонстрационные данные должны быть внутренне согласованы: сводка соответствует деталям звонков, ошибки загрузки не входят в число принятых, дубликаты не создают записи, доля нарушений использует число успешных звонков.
- Готовый батч не имеет опубликованной оценки; постановка в очередь доступна только команде, повтор не создаёт задание.
- При частичной загрузке видны успешные записи, дубликаты и конкретные ошибки; при нуле принятых нет состояния готовности.
- До завершения всего батча отчёт недоступен; после завершения без успешных записей отображается «Нет данных», а не нулевая средняя.
- При критическом нарушении и включённом правиле итог равен 0, исходные 11 оценок остаются видны. При выключенном правиле факт нарушения остаётся, итог равен обычной сумме.
- Для неприменимого критерия и отключённого темпа отображаются 1 и корректные пояснения.
- Восстановление сохраняет идентификатор загрузки, стрим и исходный состав; новый независимый анализ получает другой идентификатор.
- Сравнение разрешает только завершённые батчи одного стрима. Для отсутствующих средних виден текст отсутствия данных.
- Создание на основе стрима даёт новый ID; удаление требует подтверждения конкретного стрима и описывает удаление истории. Отмена подтверждения ничего не удаляет.
- Проверяются узкий экран, длинная транскрипция, раскрываемые пояснения, табличная прокрутка, клавиатура и видимый фокус.
- В рабочем режиме сетевой сбой показывает ошибку с повтором без перехода в демо; отклонённый ключ предлагает переподключение. Выход очищает сохранённое подключение.
- В первой поставке проверяются сборка, браузерные сценарии и отдельные проверки компонентов. Реальные интеграционные проверки выполняются после готовности соответствующих операций backend.
- На этапе этой спецификации тесты приложения не запускаются: код ещё не создан. Проверяется целостность самой документации.

## Out of Scope

- Реализация или изменение backend, хранение результатов, очередь обработки и внутренние алгоритмы стрима.
- Обработка аудио на frontend, реальные вызовы Whisper/LLM и выдача демонстрационных данных за результат анализа загруженных файлов.
- Работающий end-to-end REST в первой демонстрационной поставке; он подключается следующим этапом, когда backend доступен.
- Пользовательские учётные записи, пароли, отзыв и замена ключей, удаление заказчиков, отключение стримов.
- Редактирование существующего стрима под прежним ID, сравнение разных стримов, перезапуск одной ошибочной записи.
- Обратная связь сотруднику внутри системы и дополнительные запросы к LLM для сводки.
- Экспорт CSV/XLSX/PDF и постоянный аудиоплеер отчёта.
- Новые лимиты загрузки, ночное расписание тестовой версии и внешнее файловое хранилище.
- Буквальное копирование демонстрационного меню, условных цифр и элементов просмотрщика скриншотов.
- Публикация приложения, изменение GitLab или отправка сообщений разработчику backend в рамках подготовки этой спецификации.

## Уточнение формы стрима — 2026-10-08

Сайт скрывает модель Whisper, язык, промпт распределения ролей, модель LLM
и оба промпта LLM в форме и снимке. Эти параметры нового стрима подставляет
backend из действующих Python-источников и фиксирует в снимке. Whisper-промпт
подставляется через административный REST-запрос и остаётся редактируемым.
Копирование переносит прежний Whisper-промпт, опции и пороги; материалы выбирают
заново, новый ID обязателен. Старые стримы сохраняются без изменения.
Демо использует явно обозначенную демонстрационную подсказку, без запросов API.


## Уточнение входа — 2026-10-08

В форме входа только API-ключ. Адрес backend задаётся при развёртывании сайта;
пользователь его не вводит и не меняет. Рабочие запросы используют `/api/v1`
через настроенный прокси, права/организацию определяет сервер по ключу.
