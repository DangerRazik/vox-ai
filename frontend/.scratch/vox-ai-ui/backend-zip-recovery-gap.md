# Разрыв контракта восстановления ZIP — 2026-10-08

Обнаружен при реализации frontend №14. Исправление разрешено пользователем 2026-10-08 и реализовано в соседнем backend.

## Подтверждение через настоящий REST

Изолированная временная БД/материалы, настоящий ffprobe и call_002.mp3.
Модели недоступны; для подготовки общей ошибки временно убран файл базы знаний
тестового стрима. Проверка состояния выполнялась только через API.

1. `POST /v1/batch-archives` → 201, `ready`, одна принятая запись.
2. После ручного запуска с недоступным материалом → `batch_failed`,
   `batch_processing_failed`. Материал возвращён перед восстановлением.
3. Повтор того же ZIP/upload_id/stream_id → 200, **тот же батч**, `restoring`.
4. `POST /v1/batches/{id}/complete` → 409 `archive_managed`.

Текущий импортёр переводит батч в restoring через create, но не регистрирует
восстановительный приём архива и не передаёт записи повторно. Успех HTTP 200
не означает готовность восстановленного батча. Прямой /files также защищён
проверкой archive_managed и не заменяет ZIP-восстановление.

## Предлагаемое минимальное дополнение backend

Сохранить существующий `POST /v1/batch-archives`, multipart и серверные права.
В состоянии restoring зарегистрировать защищённый приём, повторно передать
элементы через существующую проверку исходных хешей/метаданных, завершить
через существующую проверку restoration_receipts. Только полный исходный
состав переводит батч в ready. Новый upload_id, батч или анализ не создаются.

Перепаковка/переименование допустимы в пределах существующего правила состава
по содержимому; пропущенные метаданные сохраняют исходные значения. Посторонняя
запись, конфликт метаданных и неполный состав объясняются существующими 409.
Независимые загрузки, идемпотентные повторы закрытых батчей, публикация и ручной
запуск сохраняют текущие правила. Изменение требует отдельного разрешения,
так как AGENTS frontend и тикет №14 исключают реализацию backend.

Frontend-загрузка, сохранение upload_id, чтение фактического состояния и
контролируемые проверки могут выполняться независимо от этого дополнения.

## Исправление и проверка

Импортёр регистрирует приём в состоянии restoring, сохраняет исходные проверки
хешей/метаданных и завершает только после проверки всех restoration_receipts.
Неполный состав — restoration_incomplete, новая запись — composition_conflict,
изменённые метаданные — metadata_conflict. Перепаковка и переименование допускаются;
пропущенные метаданные сохраняются. После успешного восстановления его манифест
становится эталоном идемпотентного повтора ZIP. До успешного восстановления
закрытый исходный манифест сохраняется.

REST-регрессия проверяет полный состав, конфликты, повтор, перезапуск API,
неизменность call_id/batch_id/upload_id/stream_id и отсутствие отчёта до анализа.
Живая frontend-проверка через настоящий HTTP, аудио и ffprobe прошла: один
принятый звонок, дубликат, ошибочный файл; reload сохраняет ID, восстановление
возвращает тот же батч в ready. Модели отключены; запуск для подготовки сбоя
выполняет только тестовый стенд. Frontend не вызывает запуск.
