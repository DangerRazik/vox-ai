# API заказчиков — задача №03

Реализованы создание организации, одноразовая выдача ключа, чтение и авторизация.
Модели Whisper/LLM не вызываются. Pipeline и CLI не изменены.

## Запуск

Из корня репозитория в PowerShell:

```powershell
$env:VOX_ADMIN_API_KEY = Read-Host 'Административный ключ (минимум 24 символа)' -MaskInput
$env:VOX_DATABASE_PATH = 'C:\Users\User\PycharmProjects\call_anlyzer\data\vox.sqlite3'
& 'C:\Users\User\PycharmProjects\call_anlyzer\.venv-backend\Scripts\python.exe' -m uvicorn backend.api:create_app --factory --host 127.0.0.1 --port 8000
```

Секрет задаётся операционно; значения по умолчанию для административного ключа нет.
При публикации вне localhost необходим HTTPS; не включать отладочный вывод секретов.
Для других рабочих каталогов следует явно задавать абсолютный VOX_DATABASE_PATH.

## Контракт

Все защищённые запросы: `Authorization: Bearer <key>`.

| Запрос | Права и результат |
| --- | --- |
| GET /v1/access-context | По текущему Bearer-ключу: роль и своя организация; Cache-Control: no-store |
| POST /v1/admin/customers, JSON `{"name":"Организация"}` | Только администратор, 201: customer_id, name, created_at, api_key; Cache-Control: no-store |
| GET /v1/admin/customers | Только администратор, items со всеми организациями без ключей |
| GET /v1/customers/{customer_id} | Своя организация либо администратор; чужая/отсутствующая — 404 |
| GET /v1/streams; GET /v1/batches | Авторизованный запрос; пока items пустой, создание ресурсов появится в задачах 04/05 |

Фильтр customer_id в списках доступен администратору; заказчик не может выбрать
чужого владельца (404). Клиентские аккаунты, ротация и отзыв ключей не реализованы.
401 означает отсутствующий/неверный ключ, 403 — административная операция с ключом
заказчика, 422 — неверный запрос. Ошибки имеют error.code/message/details и не
включают исходные тела запросов либо секреты.

Ключ — 32 случайных байта в URL-safe представлении; в БД хранится только SHA-256.
Это хеш высокоэнтропийного машинного ключа, не схема хранения пользовательских
паролей. Сохраните ключ из ответа создания: повторно получить его нельзя.
Обычные ответы используют явный список публичных полей. Не использовать имена
организаций для передачи секретов; права доступа к файлу БД обеспечиваются ОС.

## Контекст подключения frontend №12

2026-10-08 пользователь разрешил минимальное расширение backend для frontend-тикета
№12. `GET /v1/access-context` использует существующую авторизацию. Ключ заказчика
возвращает `{"role":"customer","customer":{"customer_id":"<uuid>","name":"<name>"}}`,
включая организацию без стримов и батчей. Ключ команды возвращает
`{"role":"admin","customer":null}`. Отсутствующий/неверный ключ — 401. Ключи,
хеши, настройки стримов и прочие организации в ответ не входят. Ответ не кэшируется.

Frontend использует `/api/v1` через локальный dev-прокси к `http://127.0.0.1:8000/v1`.
Промпты, обработка звонков, CORS и существующие операции backend не изменены.
REST-проверка контекста находится в `tests/test_customer_api.py`.

## Окружение и проверка

Подготовлено отдельное окружение `.venv-backend` на Python 3.14.7 из официального
NuGet-пакета Python с DLL SQLite 3.53.4 из официального архива sqlite.org.
Базовый runtime находится в `.runtime/python-3.14.7/tools`; нельзя удалять его,
не пересоздав окружение. Системный Python и исходная `.venv` не изменены.
Runtime, окружение и data исключены из Git. Установленные версии REST-библиотек
зафиксированы в requirements.txt. На другой машине необходимо отдельно
подготовить runtime с исправленной SQLite; pip не обновляет системную SQLite.

Backend проверяет согласованный диапазон исправленных версий SQLite при запуске.
Соединения включают WAL, foreign_keys и busy_timeout=5000, закрываются после
короткой транзакции. Схема customers создаётся идемпотентно при старте.

Автотесты используют публичный API и реальную SQLite во временном каталоге:

```powershell
& 'C:\Users\User\PycharmProjects\call_anlyzer\.venv-backend\Scripts\python.exe' -m unittest discover -s tests -v
```

Покрыты сохранение ключа после пересоздания приложения, изоляция двух организаций,
административное чтение, пустые списки, запрет клиентского административного доступа,
ошибки авторизации и отсутствие отражения секретов в ошибках валидации.
