# Vox AI: критерии приёмки будущей реализации

Статус: план проверок к [проекту backend](backend-design.md). Проверки не выполнялись: сейчас изменяется документация, работающего REST/worker/БД ещё нет.

## Приём и принадлежность

1. Ключ заказчика позволяет видеть только его стримы, батчи и отчёты. Попытка связать батч с чужим стримом отклоняется; административное чтение всех заказчиков разрешено.
2. API-батч создаётся, получает файлы несколькими запросами и становится ready только после complete. Пустой или ещё принимающий файлы батч не запускается.
3. ZIP без пароля с подпапками формирует один батч выбранного стрима. При наличии корректных записей они принимаются, ошибки остальных видны отдельно. При нуле принятых записей загрузка неуспешна.
4. Поля employee/date можно опустить. Файл не отклоняется из-за размера, количества, длительности или расширения на основании продуктовой квоты; неподдерживаемый реальными средствами файл получает объяснимую ошибку.
5. Одинаковое содержимое в одном батче создаёт одну запись независимо от имени. Повтор HTTP/ZIP с прежним upload_id не увеличивает счётчики; иной upload_id допускает независимый новый анализ.
6. После complete состав фиксирован. Изменение стрима или состава с прежним upload_id отклоняется. Повтор неизменённой завершённой загрузки возвращает исходный батч.

## Стрим и обработка

7. Изменение любого согласованного параметра/материала создаёт новый stream_id. Старый батч продолжает ссылаться на прежний контекст; неизменяемые файлы не перезаписываются.
8. Запуск доступен только команде Vox AI. FIFO соответствует времени принятия ручного запуска, а повтор start не создаёт новую задачу и не меняет позицию.
9. Два конкурирующих запуска одного батча дают одну задачу. Два запущенных экземпляра worker не обрабатывают звонки одновременно; загрузки/чтения REST доступны во время моделирования.
10. Порядок вызовов соответствует репозиторию: Whisper/коррекция → разметка ролей → диалог/метрики → база знаний → оценка. Обычно есть два логических LLM-запроса; сводка и сравнение не вызывают LLM.
11. Включённые словарные опции используют обязательные материалы; отключённый темп даёт 2.2=1 с пояснением. Согласованные ограничения 11 критериев/шкалы сохраняются даже при особенностях нормализации прототипа.
12. Одна ошибка записи не останавливает остальные. JSON/технические ошибки сервиса фиксируются для записи по существующему поведению; дополнительный LLM-запрос для исправления результата не выполняется.

## Оценки и отчёты

13. Успешный результат содержит 11 критериев с исходными оценками 0/0.5/1; критерий 5.2 бинарный. Неприменимость отражена баллом 1 и пояснением.
14. При критическом нарушении и включённом флаге итог равен 0 из 11, исходные оценки остаются. При выключенном флаге итог равен сумме. Базовый флаг включён.
15. До завершения и commit аналитических результатов в БД нет, итоговый отчёт не доступен. После commit доступны подробные отчёты и сводка.
16. Пример: 100 файлов, 10 отклонены, из 90 записей 80 успешны и 10 ошибочны. Отчёт показывает 90/80/10 и отдельно 10 ошибок загрузки; средние используют 80 успешных звонков.
17. Когда все принятые записи ошибочны, батч completed с опубликованными ошибками/счётчиками, средние и доля критических нарушений null. Это не batch_failed.
18. Сравнение возвращает показатели выбранных completed-батчей одного стрима, без смешивания других стримов/заказчиков и без нового анализа.

## Целостность, рестарт и очистка

19. Принудительная ошибка в середине фиксации результатов не оставляет ни одного нового исхода/критерия/отчёта этого батча. Статус завершения не публикуется; батч получает batch_failed отдельной служебной операцией.
20. Если commit прошёл, но подтверждение потеряно, повтор загрузки/start возвращает сохранённый результат без повторного анализа и двойной записи.
21. При рестарте сохраняются queued-порядок и загрузочная метаинформация. Ещё не начатые запущенные батчи продолжаются; прерванный незавершённый батч получает batch_failed и не переигрывается автоматически.
22. Восстановление batch_failed требует повторного приёма исходных файлов с прежним upload_id, затем ручного start. Обрабатывается весь батч, формируется только один опубликованный набор.
23. После успешного commit входные аудио/ZIP удаляются, включая входы завершённого батча с ошибками отдельных записей. После ошибки всего батча входы остаются. Материалы стрима и история БД не очищаются вместе с входами.
24. Ошибка очистки после commit сохраняет completed и отчёт. Очистка повторяется без Whisper/LLM. После рестарта завершённый батч с ожидающей очисткой не объявляется ошибочным.
25. Удаление стрима удаляет связанные строки БД и управляемые каталоги, включая его очередь, транскрипции и отчёты. Данные другого стрима/заказчика сохраняются. Активный приём/обработка защищены предложенным техническим guard из проекта; исторические данные не исчезают по таймеру.
26. Изменение модельных идентификаторов/влияющих параметров создаёт новый стрим; уже созданный стрим продолжает использовать свой снимок. Фактически использованные идентификаторы записаны без секретов.
27. Неуспешная попытка освобождает старое задание очереди. Восстановленный батч получает новый sequence; атомарный захват задания и удаление стрима не могут одновременно разрешить запуск удалённого стрима.
28. Противоречащий 5.2 флаг LLM не меняет канонический признак нарушения: подробный отчёт, итог и сводка согласованы с исходной оценкой 5.2.
29. Сбой сразу после транзакции удаления стрима не теряет очистку каталогов: CleanupJob был зарегистрирован в той же транзакции и пережил каскады.
30. Повторный запрос восстановления не сбрасывает поколение. Прежние файлы на диске не позволяют обойти повторный приём; файл с прежним call_id отмечается в новом поколении и может завершить восстановление.

## Порядок валидации

По уточнению пользователя от 2026-10-06 запросы к Whisper и LLM в приёмочных проверках должны быть реальными, без заглушек моделей. Проверки выполняются на изолированных временных БД и файловых директориях с согласованными тестовыми записями и настроенными реальными сервисами. Сценарии, не требующие анализа (например, отказ чужому ключу, пустому батчу, чтение сравнения или повтор очистки), не вызывают модели искусственно.

Сначала выполняется малый живой сценарий и проверки транзакций/повторов/FIFO/изоляции и входов. Сбои локальной фиксации, рестарт и ошибки очистки проверяются контролируемыми локальными условиями, без подмены результатов моделей. Проверяются структура и бизнес-инварианты результата, а не дословное совпадение текста модели; ожидаемые агрегаты рассчитываются из фактических результатов запуска. Недоступность сервиса отмечается как невозможность завершить соответствующую проверку, а не как успешная приёмка.

Затем отдельным запуском измеряется батч порядка 300 звонков по 5 минут: фиксируется фактическая длительность, обещание скорости или ночной SLA не задаётся. Живые вызовы могут расходовать оплачиваемые ресурсы и передают данные внешним сервисам; используются разрешённые тестовые записи, секреты не включаются в отчёты. В рамках подготовки спецификации живые запросы не выполнялись.

Факт прохождения этих проверок будет записан после реализации. Наличие этого документа не означает, что тесты уже созданы или прошли.
