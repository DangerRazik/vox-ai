# ZIP-загрузка через REST API

Реализованный endpoint №07: `POST /v1/batch-archives`. Он предназначен для
пользователя заказчика и требует `Authorization: Bearer <customer-key>`.
Организацию определяет ключ; `customer_id` в multipart не передаётся.
Административный ключ не создаёт загрузку от имени выбранного заказчика.

## Запрос

С 2026-10-09 интерфейс загрузки/восстановления не предлагает JSON-метаданные;
способ передачи сотрудника и даты ещё не согласован. Поддержка `metadata_file`
в REST сохранена для совместимости внешних клиентов.

Ответы батча (`POST` ZIP, список и сведения) содержат `name` — исходное имя ZIP
без расширения, и `archive_name` — имя архива с расширением. Имена берутся из
сохранённого `batch_archives.original_name`; миграция не требуется. Первое имя
сохраняется при повторе и восстановлении. Если имени нет, значения равны `null`.
Идентификаторы и независимость загрузок с одинаковыми именами сохраняются.

| Поле multipart | Содержимое |
| --- | --- |
| `upload_id` | UUID исходной загрузки; сохраняется при повторе. |
| `stream_id` | UUID доступного стрима. |
| `archive` | ZIP без пароля. Формат определяется содержимым. |
| `metadata_file` | Необязательный JSON в UTF-8 с метаданными по относительным путям. |

```json
{"calls/001.wav":{"external_employee_id":"employee-17","called_at":"2026-10-07T10:00:00Z"}}
```

Employee ID и дата необязательны, допускают `null`. Дата — ISO 8601 с часовым
поясом. Неизвестные поля, повторяющиеся JSON-ключи и метаданные отсутствующих
элементов отклоняются. Служебный JSON внутри ZIP не требуется.

Обычные подпапки поддерживаются; каталоги не являются записями звонков. Вложенные
архивы не раскрываются: такой файл проверяется как аудио. Whitelist аудиорасширений
и продуктовых квот нет. Абсолютные пути, переходы `..`, Windows-разделители/диски,
ссылки и специальные файлы получают отказ по элементу. Имена не используются
как пути записи: аудио хранится под внутренними идентификаторами backend.

## Ответы и ошибки

Первый запрос возвращает 201 с полями батча и `items`; повтор — 200.
`items` имеет тот же формат, что `GET /v1/batches/{batch_id}/files`:

- `accepted`: исходное имя, `call_id` и nullable метаданные;
- `duplicate`: имя дубликата, исходный `call_id` и `duplicate_of` с исходным именем;
- `rejected`: исходное имя, `file_id`, `error.code` и `error.message`.

Если явно переданные метаданные дубликата противоречат принятой записи, этот
элемент получает отказ `metadata_conflict`; исходные метаданные сохраняются,
приём последующих элементов продолжается.

При хотя бы одной принятой уникальной записи статус — `ready`, ожидается ручной
запуск командой Vox AI. Корректные записи принимаются независимо от непригодного
аудио, небезопасных путей и повреждённых элементов. При нуле принятых записей
статус — `upload_failed`, запуск запрещён. Ошибки загрузки не входят в
`total_calls` или `processing_errors`; повтор не увеличивает счётчики.

Нераспознаваемый ZIP, пустой архив, архив с паролем или неверный JSON метаданных
возвращают 422 с кодом `invalid_archive`, `empty_archive`, `encrypted_archive`
или `invalid_metadata`. В `error.details.batch` возвращается исходный батч,
что позволяет сохранить его ID и показать состояние загрузки. Исправление
неудачного первоначального импорта допускается с прежним `upload_id`.

Недоступность ffprobe — 503 `audio_probe_unavailable`, без фиктивной ошибки
файла. Частично принятые записи и ZIP сохраняются, загрузка остаётся `uploading`;
повтор того же ZIP продолжает приём через дедупликацию.

## Повторы и фиксация состава

Перепаковка с теми же путями, содержимым элементов и метаданными возвращает
существующий батч. Порядок элементов, сжатие и даты ZIP не определяют его
идентичность. Изменение входов/метаданных закрытого батча либо стрима с прежним
`upload_id` — 409 `upload_conflict`. Новый `upload_id` создаёт независимый батч.

На весь импорт регистрируется активный приём. Одновременный импорт и внешнее
завершение отклоняются с 409 `upload_in_progress`. ZIP управляет составом своего
батча; отдельное добавление файла в открытый ZIP-батч — 409 `archive_managed`.
После прерванного импорта внешний `complete` также возвращает `archive_managed`,
даже когда активный HTTP-запрос уже закончился: завершение разрешается только
импортёру после повторного приёма всего ZIP.
После автоматического завершения обычные загрузки возвращают `upload_closed`.

После атомарной публикации отчёта worker удаляет управляемую копию ZIP и принятые
аудиофайлы; результаты, имена, транскрипции и материалы стрима сохраняются.
Ошибка обработки всего батча сохраняет входы. Устойчивые повторы очистки реализованы
в №10 и охватывают весь каталог батча, включая ZIP. №09 реализует восстановительный
приём отдельных файлов. Разрешённое исправление при интеграции frontend №14
подключает ZIP к тем же проверкам восстановления: прежний upload_id/stream_id,
защищённый активный приём, сверка содержимого и сохранённых метаданных.
Новая запись — 409 composition_conflict, изменённые явные метаданные —
409 metadata_conflict (восстановление не завершается), неполный набор —
409 restoration_incomplete. Принятые части сохраняются для продолжения,
состав остаётся исходным, новый batch_id/call_id не создаётся. ready возвращается
только после приёма всех исходных записей. ZIP можно перепаковать/переименовать
элементы, метаданные опустить; сохранённые значения остаются. После успешного
восстановления новый ZIP-манифест используется для идемпотентного повтора.
Восстановление не запускает обработку: нужен ручной start команды. Аварийное завершение API может
оставить `active_uploads`; безопасное восстановление этих регистраций ещё требуется.

Удаление стрима в №13 удаляет также `batch_archives`, `upload_errors` и
`file_duplicates` в общей транзакции. Активный импорт блокирует удаление;
если удаление завершилось перед регистрацией повтора ZIP, импорт получает 404.

## Сопоставление с подготовленным frontend

Проверены `frontend/src/app/uploads/upload-models.ts` и
`frontend/docs/integration.md` (соседний репозиторий). Multipart соответствует
запланированным полям `upload_id`, `stream_id`, `archive`, `metadata_file`.
Будущий REST-адаптер преобразует `items` в `accepted`, `duplicates`, `errors`
интерфейса `UploadResult`: имя — `original_name`, исходное имя дубликата —
`duplicate_of`, причина отказа — `error.message`. Подстановка демо при ошибке
REST не требуется. Frontend в №07 не изменяется; подключение адаптера — его
отдельная задача. Контекст ключа и поля списка батчей остаются отдельными
вопросами интеграции, а не частью ZIP-импорта.

## Проверки

```powershell
.\.venv-backend\Scripts\python.exe -m unittest tests.test_archive_api -v
$env:RUN_LIVE_ARCHIVE_TEST = '1'
.\.venv-backend\Scripts\python.exe -m unittest tests.test_live_archive -v
Remove-Item Env:RUN_LIVE_ARCHIVE_TEST
```

Живой сценарий использует две разные записи из репозитория (`call_001.mp3`,
`call_002.mp3`) либо `VOX_LIVE_AUDIO`/`VOX_LIVE_AUDIO_SECOND`, настоящий HTTP API,
отдельный worker, ffprobe и настроенные Whisper/LLM. Модельные вызовы потенциально
платные. БД и входы временные; исходные файлы и рабочие данные не меняются.
Сводка сверяется с фактическими результатами двух записей, а очистка — с
существовавшими до запуска управляемыми файлами. Повтор после завершения
возвращает тот же отчёт и не восстанавливает удалённые входы.

Приёмка 2026-10-07: живой сценарий прошёл за 60,387 секунды с Whisper
`whisper-large-v3` и LLM `kimi-k2.7-code`: 2 успешные записи, 2 ошибки загрузки,
1 дубликат, согласованные отчёты и удалённые входы. После исправлений ревью
финальная обычная suite — 41 прошедший тест и 4 opt-in пропуска; контекст —
3 прошедших и 1 opt-in пропуск. Две Spec-регрессии исправлены и проверены;
открытых замечаний Standards/Spec нет.
