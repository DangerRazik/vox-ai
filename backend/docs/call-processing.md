# Обработка звонка внутри стрима

По решению пользователя от 2026-10-05 дальнейшие решения об обработке звонков берутся из реализации репозитория. Основа описания — коммит `77a13481af15ceb61b7a31cc25ab949352d70f39`; код при документировании не изменялся. Ранее согласованные требования и настройки стрима сохраняются, отличия от прототипа перечислены ниже.

## Порядок обработки

Порядок задан в [pipeline.py](../pipeline.py):

1. `transcribe(audio_path)`: запрос Whisper, разбор ответа и словарная нормализация текста реплик.
2. `assign_roles(segments)`: отдельный запрос к LLM для назначения ролей сотрудника и клиента либо резервное назначение ролей.
3. `to_dialog_text(segments)`: сборка диалога с ролями и таймкодами.
4. `compute_metrics(segments)`: расчёт метрик по тексту и временным границам реплик.
5. `load_knowledge_base(kb_path)`: чтение и очистка базы знаний.
6. `analyze_call(dialog, kb_text, metrics)`: запрос оценки к LLM и обработка результата.
7. Добавление `_segments` и `_metrics` в результат звонка.

Таким образом, для обычного звонка с двумя распознанными говорящими выполняются два логических запроса к LLM: разметка ролей и оценка. Разметка ролей происходит до расчёта метрик, а не объединяется с оценкой на третьем этапе. Для сводного отчёта батча дополнительного запроса к LLM нет.

Три бизнес-этапа стрима сохраняются: транскрибация, подготовка транскрипции и метрик, оценка LLM. В прототипе нормализация текста входит непосредственно в `transcribe`; разметка ролей является подготовкой к дальнейшей обработке транскрипции.

## Транскрибация и нормализация

Источник: [transcriber.py](../transcriber.py).

Whisper вызывается HTTP-запросом `POST /audio/transcriptions`. Передаются аудиофайл, модель, язык, промпт, `response_format=json` и `temperature=0`; таймаут клиента — 900 секунд. Адрес и ключ сервиса берутся из настроек и не являются API-ключами заказчиков Vox AI.

Ответ разбирается в следующем порядке:

| Форма ответа | Разбор |
| --- | --- |
| `transcription` | Строки с временными границами `[HH:MM:SS -> HH:MM:SS]`, идентификатором `SPEAKER_XX` и текстом; дробные секунды поддерживаются. |
| `segments` | Для каждой реплики читаются `start`, `end`, `speaker`, `text`. Отсутствующий идентификатор заменяется на `SPEAKER_00`. |
| `text` | Создаётся одна реплика с нулевыми временными границами и идентификатором `SPEAKER_00`. |
| Ни одной поддерживаемой формы | Возникает ошибка обработки. |

Внутренние временные границы задаются в секундах от начала записи. Парсер строковой формы сохраняет совпавшие фрагменты; при отсутствии совпадений возвращает пустой список. Проверки порядка реплик и корректности временных интервалов в прототипе нет.

Коррекция текста использует таблицу замен `WHISPER_FIXES`: ошибочное написание → правильное написание. Ключи применяются от длинных к коротким, совпадения регистрозависимы, специальные символы экранируются, соседство с латинскими и кириллическими буквами ограничивает совпадение. Пустая таблица означает отсутствие замен. Перед запросом разметки ролей первые 15 реплик нормализуются повторно.

## Назначение ролей

Источник: `assign_roles` в [transcriber.py](../transcriber.py).

- При пустом списке обработка ролей возвращает пустой список.
- Если распознан один говорящий, всем репликам назначается `OPERATOR` без запроса к LLM.
- Иначе LLM получает первые 15 реплик в форме «идентификатор говорящего: текст», без аудио и временных меток. Промпт описывает признаки сотрудника и клиента.
- Ответ ожидается в виде сопоставления `operator` и `client` идентификаторам говорящих. Код проверяет и использует идентификатор `operator`; остальные говорящие получают `CLIENT`.
- При ошибке запроса или разбора ответа либо неизвестном идентификаторе сотрудника используется первый идентификатор после сортировки говорящих.

Запрос разметки выполняется через OpenAI SDK к настроенному API: JSON-режим, `temperature=0`, таймаут HTTP-клиента — 120 секунд. Промпт разметки в прототипе содержит контекст компании исходного проекта.

Текст для оценки содержит строки `[MM:SS] OPERATOR|CLIENT: текст`. Используется время начала реплики с отброшенной дробной частью секунд; время окончания и исходный идентификатор говорящего остаются в `_segments`.

## Метрики второго этапа

Источник: [acoustics.py](../acoustics.py). Метрики вычисляются по тексту, ролям и временным границам реплик, без анализа звукового сигнала.

| Метрика | Расчёт в прототипе |
| --- | --- |
| Длинные паузы | Для соседних реплик разница между началом следующей и окончанием предыдущей не меньше порога `LONG_PAUSE_SEC`, в исходных настройках 3 секунды. |
| Перебивания | Та же разница не больше `INTERRUPTION_GAP_SEC`, в исходных настройках 0.2 секунды, при смене роли. Отрицательные промежутки также учитываются. |
| Темп сотрудника и клиента | Для каждой реплики число слов, определяемых `\w+`, делится на длительность с нижней границей 0.1 секунды. Затем берётся среднее скоростей реплик соответствующей роли: слова в секунду, округление до двух знаков. |
| Маркеры неуверенности | Сумма вхождений подстрок «наверное», «возможно», «не знаю», «не уверен», «как бы», «ну» в тексте сотрудника, приведённом к нижнему регистру. |
| Маркеры грубости | Аналогичный подсчёт «алло», «мужчина», «женщина», «девушка», «молодой человек», «вы меня не понимаете», «я же знаю». |
| Длительность | Окончание последней реплики минус начало первой, округление до двух знаков. |

Для пауз и перебиваний сохраняются счётчики и сведения о соответствующих репликах, включая фрагменты текста до 80 символов. При отсутствии реплик возвращается пустой набор метрик; при отсутствии реплик конкретной роли её темп равен 0. Маркеры считаются как подстроки, без проверки контекста.

Согласованное дополнение: если анализ темпа отключён в стриме, критерий «Темп разговора» получает 1 с пояснением «анализ темпа отключён».

## База знаний и запрос оценки

Источники: [kb.py](../kb.py), [analyzer.py](../analyzer.py).

База знаний читается из файла как байты, декодируется через quoted-printable и UTF-8. Если обнаружено HTML-представление, извлекаются тексты заголовков `h1`, `h2`, `h3` и ячеек `td`; затем сжимаются пробелы и пустые строки. Это описание существующего загрузчика, а не универсального обработчика документов Word.

В запрос оценки входят чек-лист, первые 20 000 символов очищенной базы знаний, JSON метрик и собранный диалог. LLM вызывается через OpenAI SDK к настроенному API, с `temperature=0` и JSON-режимом; таймаут HTTP-клиента — 120 секунд.

Промпт требует пройти все критерии, учитывать смысл и перефразирование, сверять ответы сотрудника с базой знаний и отмечать отсутствие в ней ответа. Неприменимому критерию присваивается 1 с пояснением. Для критического нарушения запрашиваются цитата и объяснение; рекомендации должны быть конкретными и привязанными к критериям, 3–5 пунктов.

Содержимое базы знаний закреплено за стримом. Изменение содержимого требует нового идентификатора стрима согласно [ADR-0001](adr/0001-immutable-streams.md).

## Правила 11 критериев

Полные исходные формулировки: `CHECKLIST` в [checklist.py](../checklist.py). По указанию пользователя эти правила служат основой первой версии, с ранее согласованными настройками стрима.

| ID | Критерий | Правила исходной реализации |
| --- | --- | --- |
| 1.1 | Приветствие | 1 — своевременное приветствие, компания и имя названы до вопроса клиента, соблюдён речевой модуль; 0.5 — свободная форма без полной стандартной формулы; 0 — приветствие после клиента или отсутствует. |
| 1.2 | Прощание | 1 — сотрудник инициировал прощание, уточнил вопросы и произнёс стандартную формулу; 0 — мог попрощаться, но не сделал этого. Если клиент завершил разговор раньше, ставится 1. |
| 2.1 | Наличие слов вежливости | 1 — присутствуют общепринятые формулы вежливости и при ошибке принесены извинения; 0 — слов вежливости нет. |
| 2.2 | Темп разговора | 1 — умеренный темп, подстройка под клиента, чёткая дикция, отсутствие монотонности; 0 — неоправданный быстрый или медленный темп либо клиент прерывается из-за скорости. |
| 2.3 | Тон разговора | 1 — доброжелательный, спокойный, партнёрский тон; 0.5 — до трёх случаев потери контроля эмоций или командных интонаций; 0 — раздражение, повышение голоса или монотонность. |
| 2.4 | Грамотность и культура речи | 1 — грамотная речь без перечисленных в чек-листе нарушений; 0.5 — не более трёх ошибок; 0 — грубость, ненормативная лексика либо систематические нарушения. |
| 3.1 | Активная позиция и демонстрация внимания | 1 — ведёт разговор, слушает, отвечает по существу и комментирует ожидание, активное слушание уместно, нет посторонних звуков; 0.5 — отсутствует один пункт либо активное слушание избыточно; 0 — перебивает, не слушает или присутствуют посторонние звуки. |
| 3.2 | Работа с конфликтом | 1 — даёт высказаться, присоединяется, предлагает решения и сохраняет спокойствие; 0 — замечания о грубости клиента, снисходительность, высокомерие или сарказм. |
| 4.1 | Постановка/снятие удержания | 1 — корректно предупредил, поблагодарил, при необходимости продлил ожидание с сообщением или попросил перезвонить; 0 — необходимые фразы не прозвучали. |
| 5.1 | Соблюдение скрипта и регламента | 1 — процедуры соблюдены, информация полная и корректная по базе знаний, ответ структурирован; 0.5 — отсутствует один пункт либо есть непонятные профессионализмы; 0 — нарушение процедур, неверный или неполный ответ, перекладывание ответственности. |
| 5.2 | Критическое нарушение | 1 — нарушений нет; 0 — неверная консультация или оформление, обман, дискредитация компании, обесценивающие высказывания, негативный отзыв о компании либо оценочные комментарии о системах или сотрудниках. |

Каждый критерий имеет максимум 1. Для критериев 1.2, 2.1, 2.2, 3.2, 4.1 и 5.2 в исходных формулировках описаны только значения 0 и 1. Общая допустимая шкала — 0, 0.5, 1; критерий 5.2 по отдельному решению пользователя строго бинарный. Неприменимость обрабатывается по [ADR-0002](adr/0002-inapplicable-criteria-score-one.md).

## Результат звонка

В исходном JSON поле `scores` сопоставляет идентификаторы критериев объектам с `score`, `max` и `reason`. Также предусмотрены:

- `total`, `max_total` — итог и максимум.
- `critical_violation`, `critical_violation_details` — признак нарушения и объяснение с цитатой.
- `sentiment` — тональность сотрудника и клиента: positive, neutral или negative.
- `stress_level_operator` — оценка стресса сотрудника от 0 до 10.
- `etiquette_violations` — нарушения этикета.
- `kb_check` — выявленные вопросы, корректность ответов и расхождения с базой знаний.
- `recommendations` — рекомендации.
- `_segments`, `_metrics` — обработанные реплики с исправленным текстом и ролями и рассчитанные метрики.

Эти дополнительные сведения принимаются из существующей реализации в рамках указания пользователя. Детальный внешний контракт REST API ещё проектируется.

Прототип разбирает JSON, дополняет отсутствующие канонические критерии оценкой 0 и техническим пояснением, устанавливает максимум 1 и преобразует оценки в числа. При критическом нарушении обнуляет оценки и сохраняет их исходные значения в `score_before_override`. Затем пересчитывает итог с округлением до двух знаков.

Для новой версии сохраняются согласованные требования: ровно 11 критериев, допустимые оценки, максимум 11 и управление обнулением через чекбокс стрима. Исходные оценки должны оставаться доступны для разбора звонка и сводки по критериям.

## Отличия, требующие реализации при переходе к backend

После задачи №02 обработчик принимает [явный контекст обработки](processing-context.md):
модели, промпты, словарь, пороги и путь KB передаются конкретному запуску.
Порядок этапов и алгоритмы выше сохранены; таблица ниже описывает исходный
прототип, а хранение неизменяемых стримов и новые опции остаются последующими задачами.

| Требование | Состояние прототипа |
| --- | --- |
| Настройки и материалы принадлежат конкретному неизменяемому стриму | Используются общие настройки и параметры `audio_path`, `kb_path`; сущности стрима нет. |
| Чекбоксы второго этапа | Метрики и нормализация вызываются непосредственно, чекбоксов нет. |
| Словарь коррекции из файла | Алгоритм замен реализован через `WHISPER_FIXES`; загрузка пользовательского файла словаря и привязка к стриму отсутствуют. |
| Словарь нежелательных выражений | Есть фиксированные маркеры грубости и неуверенности; отдельного настраиваемого словаря нет. |
| Ровно 11 допустимых оценок | Код не удаляет лишние ID и не проверяет принадлежность чисел допустимой шкале. |
| Обнуление определяется критерием 5.2 и чекбоксом | Код использует отдельный флаг `critical_violation` и всегда обнуляет при истинном флаге. |
| Полные временные границы и говорящие в ответе | Код допускает резервную форму только с текстом и синтетическими нулевыми границами. |

Это зафиксированные различия между реализацией и уже принятыми требованиями. Они не изменяют согласованные правила; код на этапе проектирования не исправляется. Новые вопросы об алгоритмах обработки не задаются, существующая реализация остаётся основой.
