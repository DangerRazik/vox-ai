# Приём и обработка API-батча

Для ZIP-загрузки через frontend используйте реализованный
[контракт импорта архивов](archive-api.md).

API и worker запускаются отдельными процессами из корня проекта и используют одинаковые настройки:

```powershell
.\.venv-backend\Scripts\python.exe -m uvicorn backend.api:create_app --factory --host 127.0.0.1 --port 8000
.\.venv-backend\Scripts\python.exe -m backend.worker
```

Переменные `VOX_DATABASE_PATH`, `VOX_MATERIALS_ROOT`, `VOX_INPUTS_ROOT`,
`VOX_WORKER_LOCK`, `VOX_FFPROBE_PATH`, `VOX_ADMIN_API_KEY` задаются через окружение
или `.env`. Для API и worker используйте одинаковые абсолютные пути.
`ffprobe` должен быть доступен через PATH либо `VOX_FFPROBE_PATH`.
Секреты и адреса Whisper/LLM остаются в существующей конфигурации обработки.

Для первого запуска скопируйте `.env.example` в `.env`, если локального файла
ещё нет. Заполните `WHISPER_API_KEY`, `WHISPER_BASE_URL`, `WHISPER_MODEL`,
`GPL_BASE_URL`, `GPL_MODEL` и ключ LLM `GPL_API_KEY`, если его требует шлюз.
Адреса должны соответствовать OpenAI-совместимым сервисам, которые используются
в проекте. `VOX_ADMIN_API_KEY` — отдельный административный ключ длиной от 24
символов. `.env` игнорируется Git; заполненные секреты не добавляются в коммиты.

`VOX_ADMIN_API_KEY` принадлежит команде Vox AI и даёт доступ к административным
операциям: созданию заказчиков/стримов и ручному запуску батчей. Его можно
сгенерировать локально; это не ключ Whisper или LLM. Ключ заказчика выдаётся
API при создании организации и ограничивает запросы данными этой организации.
В запросах оба вида ключей передаются как `Authorization: Bearer <key>`.

## REST-последовательность

Все запросы требуют `Authorization: Bearer <key>`.

1. Заказчик: `POST /v1/batches`, JSON `stream_id`, `upload_id` (UUID).
   Повтор идентификатора загрузки в том же стриме возвращает существующий батч.
2. Заказчик: `POST /v1/batches/{batch_id}/files`, multipart `file` и необязательные
   `external_employee_id`, `called_at`. Здесь принимается один файл за запрос.
   `ffprobe` проверяет аудиопоток; повтор содержимого не создаёт новый звонок.
   Недоступный исполняемый `ffprobe` возвращает 503 `audio_probe_unavailable`;
   файл без аудиопотока возвращает 422 `no_audio_stream`, непригодный файл —
   422 `invalid_audio`. Такой отказ сохраняется отдельно; приём остальных файлов
   продолжается. Повтор отвергнутого содержимого не увеличивает ошибки загрузки.
3. Заказчик: `POST /v1/batches/{batch_id}/complete`. Непустой батч становится `ready`.
   Пока принимается или проверяется другой файл, возвращается 409
   `upload_in_progress`; повторите завершение после окончания запроса файла.
4. Администратор: `POST /v1/admin/batches/{batch_id}/start` → `queued`.
5. Worker: `processing` → `completed` либо `batch_failed`.
6. Статус: `GET /v1/batches/{batch_id}`. Метаданные: `GET /v1/batches/{batch_id}/calls`.
7. Отчёты: `GET /v1/batches/{batch_id}/report`, `GET /v1/calls/{call_id}/report`.
   До завершения возвращается 409. Чужие идентификаторы не раскрываются (404).

`GET /v1/batches/{batch_id}/files` возвращает `items` со статусами `accepted`,
`duplicate`, `rejected`. Принятая запись содержит `call_id` и метаданные звонка;
дубликат под другим именем содержит прежний `call_id` и `duplicate_of` с исходным
именем. Отказ содержит `file_id`, `original_name` и объяснение в `error`.
Хеши содержимого и внутренние пути API не раскрывает. Повтор того же имени
дубликата не создаёт ещё один элемент.

`total_calls` считает только принятые уникальные записи. `upload_errors` в статусе
и отчёте считает уникальные отвергнутые файлы; дубликаты и недоступность ffprobe
не увеличивают этот счётчик. После закрытия состава любые загрузки возвращают
409 `upload_closed`. Явно изменённые метаданные дубликата дают
409 `metadata_conflict`. Новый `upload_id` позволяет отдельно анализировать те
же байты в другом батче.

Worker удерживает файловую блокировку, выполняет модели вне транзакции БД,
публикует исходы звонков, сводку и статус одной транзакцией. Ошибка отдельного
звонка даёт `processing_error` без оценок. При отсутствии успешных звонков
средние и доля нарушений равны `null`. Ошибка фиксации не публикует частичные
результаты. После успешной фиксации входы удаляются; сбой всего батча сохраняет их.

Итог содержит 11 критериев. Критерий 5.2 бинарный и определяет нарушение;
флаг стрима обнуляет только итог, сохраняя оценки. Отключённый темп даёт 1 по 2.2.
Отключённая коррекция и словарь нежелательных выражений не применяются.

## Устойчивая очередь (задача 08)

Ручной запуск атомарно сохраняет строку `batch_queue` и статус `queued`.
Монотонный `sequence` определяет общий FIFO всех заказчиков по принятому запуску,
а не созданию батча или точности часов. Повтор запуска возвращает 200 с текущим
состоянием, не добавляя задачу; первый принятый запуск возвращает 202.
Захват первого задания, `claimed_at` и переход в `processing` атомарны.
Публикация результатов и удаление задания тоже выполняются одной транзакцией;
ошибка батча освобождает старое задание. Новая попытка после восстановления
получит новое место очереди (восстановительный приём описан ниже, задача 09).

Worker удерживает `VOX_WORKER_LOCK` и дополнительную каноническую OS-блокировку
`<абсолютный путь БД>.worker.lock` весь срок жизни. Другой путь настройки
`VOX_WORKER_LOCK` не позволяет второму worker обойти эксклюзивность для той же БД.
Файлы блокировок не удалять во время работы процессов. БД должна быть локальной;
не используйте альтернативные hard-link пути к одному файлу БД.

Только worker после получения обеих блокировок восстанавливает состояния:
неопубликованный `processing` становится `batch_failed` с `worker_interrupted`,
входы сохраняются, оставшиеся задания продолжаются по сохранённому FIFO.
API не выполняет recovery; его перезапуск не влияет на работающий worker.
Опубликованный `completed` никогда не анализируется повторно.

Обновление существующей БД добавляет таблицу без удаления данных. У старых
`queued` без строки очереди порядок запуска до задачи 08 не был сохранён;
worker явно помечает их `batch_failed` с `queue_order_unavailable`, сохраняя
входы, вместо выдуманного порядка или вечного ожидания. Перед обновлением
остановите старый worker; не запускайте одновременно версии до и после 08.

Повторная очистка при ошибках файловой системы реализована задачей 10 (см. ниже).
Ошибки удаления после фиксации не меняют `completed` или опубликованный отчёт.

## Восстановление ошибочного батча (задача 09)

На существующем API, где `/files` принимает один файл за запрос:

1. Заказчик повторяет `POST /v1/batches` с исходными `upload_id` и `stream_id`.
   Только `batch_failed` переходит в `restoring`; идентификатор батча, исходные
   записи, их метаданные и стрим не меняются. Причина предыдущего сбоя остаётся
   видимой до нового ручного запуска. Повтор в `restoring` не сбрасывает приём.
2. Через `/files` необходимо снова передать **каждый исходный файл**. SHA-256
   должен совпадать с одной из зафиксированных записей. Имя может отличаться;
   изменённые Employee ID/дата отклоняются, отсутствие этих полей сохраняет
   исходные значения. Новый хеш получает 409 `composition_conflict`.
   Принятый повтор возвращает 200, исходный `call_id`, `duplicate: true`.
   Сохранённые входы не заменяют повторный приём. Таблица `restoration_receipts`
   сохраняет подтверждения приёма; рестарт API и повторы не обнуляют их.
   Файл сначала проверяется ffprobe и сохраняется, затем подтверждается в БД;
   при откате остаются только идентичные исходные байты, без подтверждения.
3. `/complete` до полного приёма возвращает 409 `restoration_incomplete`.
   После полного приёма переходит в `ready`; автоматического запуска нет.
4. Администратор вручную выполняет `/start`: новая попытка в хвосте FIFO,
   старые ошибка/таймстампы очищаются. Весь батч обрабатывается заново.
   Если попытка вновь прервётся, следующий цикл требует все исходные файлы.

Для `completed` повторы создания, приёма исходных файлов, завершения и запуска
возвращают существующие идентификаторы/состояние. Файлы не восстанавливаются на
диске, результаты не меняются, новое задание не создаётся. Отчёты читаются через
исходные `/report`. Изменённый состав или стрим требует нового `upload_id`.

Задача 06 остаётся открытой: эта реализация не добавляет массовый multipart,
частичный приём одного запроса или его учёт ошибок. Выполнение 09 на текущем
API вместо предварительного закрытия 06 явно согласовано с пользователем.

```powershell
$env:RUN_LIVE_RESTORATION_TEST = '1'
.\.venv-backend\Scripts\python.exe -m unittest tests.test_live_restoration -v
Remove-Item Env:RUN_LIVE_RESTORATION_TEST
```

Сценарий использует временные БД/файлы, отдельные HTTP API/worker и настоящие
Whisper/LLM для `call_002.mp3`, `call_003.mp3`. Триггер SQLite отклоняет второй
результат атомарной публикации, затем проверяются повторный приём, прерывание
worker, ещё один приём и повтор всех операций после успешной фиксации.

## Устойчивая очистка входов (задача 10)

В транзакции публикации сохраняется `input_cleanup` со статусом `pending`.
После commit worker сразу пытается очистить управляемый каталог батча целиком:
записи, включая ошибочные, ZIP и другие сохранённые входы внутри этого каталога.
При `batch_failed` задание не создаётся, входы остаются для восстановления.

`GET /v1/batches/{batch_id}` содержит отдельное поле `cleanup`: `null` до
публикации либо объект `status` (`pending`/`completed`), `error`, `attempts`,
`updated_at`. Причина удаления не попадает в поле ошибки обработки `error` батча.
Коды очистки: `input_cleanup_permission_denied`, `input_cleanup_io_failed`,
`input_cleanup_unsafe_path`. Пути и текст системных исключений не раскрываются.

Worker повторяет pending-очистку при запуске и раз в пять секунд между заданиями.
Длительный модельный вызов может отложить периодический проход до окончания батча.
После устранения причины достаточно оставить worker работающим или перезапустить
его. Очистка не обращается к Whisper/LLM, не меняет результаты и историю; отсутствие
каталога считается успехом. Если удаление прошло, но подтверждение БД не записалось,
сохранённое намерение безопасно повторяется. API сам файлы не удаляет.

Файловая блокировка батча в соседнем каталоге `<VOX_INPUTS_ROOT>-locks` защищает
от гонки с загрузкой; сам каталог блокировок не является аудиовходом и не удаляется.
Для проверки повторов уже завершённого батча временный файл располагается вне
управляемых входов, а не восстанавливает очищенный каталог. Ссылки/junction на месте
каталога батча отклоняются. Материалы, БД и другие батчи не затрагиваются.
Управляемый каталог не предназначен для внешней записи или переключения ссылок
сторонними процессами; права доступа должны разрешать запись только API/worker.

Миграция добавляет таблицу и планирует очистку старых `completed`, не меняя
аналитику. Перед обновлением остановите старый worker. Настройки путей API/worker
должны совпадать; изменение `VOX_INPUTS_ROOT` не переносит старые файлы.
ZIP-импорт из №07 не добавляется: здесь удаляется ZIP, если он уже сохранён в
управляемом каталоге батча.

```powershell
$env:RUN_LIVE_CLEANUP_TEST = '1'
.\.venv-backend\Scripts\python.exe -m unittest tests.test_live_cleanup -v
Remove-Item Env:RUN_LIVE_CLEANUP_TEST
```

Opt-in проверка на Windows использует изолированные реальные SQLite/каталоги,
настоящие Whisper/LLM и отдельные worker. Контролируемый выход сразу после commit
оставляет pending; `CreateFileW` без разрешения удаления даёт настоящий запрет
удаления ZIP. После снятия блокировки и рестарта очистка завершается без моделей,
удаляет также вход ошибочной записи и сохраняет отчёты, материалы и другой батч.

## Явное удаление стрима (задача 13)

`DELETE /v1/admin/streams/{stream_id}` доступен только административному ключу.
Успех — 204; отсутствующий или уже удалённый стрим — 404; заказчик — 403.
При `uploading`, `restoring`, `processing` или фактически активном приёме файла
возвращается 409 `resource_busy`. Завершите приём или дождитесь обработки перед
удалением. Ожидающий батч можно удалить: DELETE и claim сериализованы одной
SQLite-транзакционной блокировкой, удалённое задание не начнёт обработку.

Транзакция удаляет стрим, батчи, очередь, подтверждения восстановительного приёма,
загрузочные метаданные, все результаты и задания очистки опубликованных входов.
В той же транзакции сохраняются независимые задания `deleted_stream_cleanup`
для материалов и каталогов батчей: они не имеют FK на удалённую историю.
Ресурсы сразу недоступны через API, заказчик и соседние стримы остаются.

После commit DELETE пытается удалить файлы. Сбой не откатывает удаление истории:
pending-задания повторяет worker при запуске и раз в пять секунд между батчами.
Ошибки хранятся как `stream_cleanup_permission_denied`, `stream_cleanup_io_failed`,
`stream_cleanup_unsafe_path` без раскрытия системных путей. Отсутствующие каталоги
считаются очищенными; отказ подтверждения в БД оставляет безопасный повтор.
Повтор DELETE возвращает 404, а уже сохранённые задания продолжают выполняться.
История не удаляется по таймеру; повтор файловой очистки не вызывает модели.
Сохраняйте одинаковые пути API/worker и ограничьте внешнюю запись в каталоги.

```powershell
$env:RUN_LIVE_STREAM_DELETION_TEST = '1'
.\.venv-backend\Scripts\python.exe -m unittest tests.test_live_stream_deletion -v
Remove-Item Env:RUN_LIVE_STREAM_DELETION_TEST
```

Windows opt-in использует временную SQLite и каталоги, настоящий Whisper/LLM,
реальный запрет удаления открытого материала и новый worker для восстановления.

## Проверка объединённой реализации — 2026-10-07

Из GitLab получены №08–10 и №13 и объединены с локальными №06–07.
Упоминания незавершённого №06 и отсутствующего ZIP-импорта в описаниях приёмки
выше отражают состояние удалённой ветки на момент тех проверок. В объединённой
версии массовый приём и ZIP доступны; FIFO и очистка всего каталога совместимы
с этими входами. Удаление стрима учитывает таблицы ZIP, дубликатов и отказов
загрузки, а также активные регистрации приёма. Гонка удаления с повтором ZIP
возвращает 404 вместо ошибки сервера.

Восстановление №09 пока проверено для отдельных файлов через существующий API.
Восстановление ZIP-батча после `batch_failed` ещё требует отдельной интеграции;
успешный первоначальный импорт и его идемпотентный повтор не подтверждают её.
