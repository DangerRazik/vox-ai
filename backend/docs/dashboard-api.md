# История результатов стрима для дашборда

Backend-тикет №12: `GET /v1/streams/{stream_id}/dashboard` возвращает опубликованные
показатели батчей одного стрима. Авторизация — `Authorization: Bearer <key>`.
Ключ заказчика определяет организацию; административный ключ читает все стримы.

Ответ 200 содержит `stream_id` и массив `items`. Каждый элемент — сохранённый
сводный отчёт, совпадающий с `GET /v1/batches/{batch_id}/report` и элементом
ответа сравнения №11. Для доступного стрима без опубликованных результатов:

```json
{"stream_id":"<stream_uuid>","items":[]}
```

## Показатели и время

Каждый элемент содержит `batch_id`, `stream_id`, `total_calls`, `successful_calls`,
`processing_errors`, `upload_errors`, `average_total`, `max_total=11`,
`criterion_averages` по 11 каноническим ID, `critical_violation_count`,
`critical_violation_rate`, `processing_started_at`, `processing_finished_at`,
`processing_duration_seconds`.

Порядок — по `processing_finished_at` от раннего к позднему; при равном времени
по `batch_id` в возрастающем порядке. `processing_finished_at` — окончание
обработки всех записей перед атомарной фиксацией отчёта. Это ось истории обработки,
а не дата звонка, создания загрузки или чтения API. `processing_started_at` —
начало выполнения батча; разность даёт длительность обработки без ожидания очереди.
Серверные времена — ISO 8601 в UTC. Даже если более ранняя загрузка запущена позже,
она появляется в истории по времени завершения. Сводки не пересчитываются при чтении.

Средний итог учитывает правило обнуления, средние критериев используют исходные
оценки. Доля критических нарушений — число 0..1. Для батча без успешных звонков
`average_total`, средние критериев и доля сохраняют `null`; количество нарушений
равно 0, счётчики записей/ошибок сохраняются. Frontend показывает «Нет данных».

В историю входят только батчи выбранного стрима со статусом `completed` и
опубликованной сводкой. Загрузки, очередь, выполняемые и ошибочные попытки без
публикации исключены. Один логический батч имеет одну сводку; повтор создания,
запуска или восстановления не создаёт независимых точек истории. Другой `upload_id`
создаёт самостоятельный батч и после завершения — самостоятельную точку.

## Доступ и целостность

Без действительного ключа — 401. Чужой, отсутствующий или удалённый стрим —
404 `not_found`; неверный UUID — 422 `invalid_request`. Администратор получает
все опубликованные батчи только выбранного стрима. Чтение истории и проверка
владельца выполняются в одном снимке SQLite. Конкурентная публикация или удаление
не возвращают частичную смесь состояний: начатое до удаления чтение может вернуть
целую прежнюю историю, запрос после удаления получает 404.

Whisper/LLM не вызываются, оценки не изменяются, материалы и исходное аудио
не читаются. История остаётся доступной после очистки входов и рестарта API,
пока стрим не удалён явно.

## Интеграция отдельного frontend

`items` использует тот же формат сводки, что сравнение и отчёт. REST-адаптер
может использовать существующий `BatchSummary` из `frontend/src/app/reports/report-models.ts`:
`total_calls` → `acceptedCalls`, остальные поля сводки из snake_case → camelCase.
Для оси графика и перехода к отчёту сохраняются `processing_finished_at` и `batch_id`.
Подписи 11 критериев берутся из выбранного стрима. `null` сохраняется и
не превращается адаптером в ноль; проценты форматируются только для отображения.
Экраны и адаптер frontend в backend-тикет не входят.

## Проверки

```powershell
.\.venv-backend\Scripts\python.exe -m unittest tests.test_dashboard_api -v
$env:RUN_LIVE_DASHBOARD_TEST = '1'
.\.venv-backend\Scripts\python.exe -m unittest tests.test_live_comparison -v
Remove-Item Env:RUN_LIVE_DASHBOARD_TEST
```

Обычные тесты используют публичный REST, временные SQLite/каталоги, настоящий
ffprobe и отдельный worker. Для «Нет данных» файл удаляется до анализа; ответы
моделей не подменяются. Проверяются обратный порядок ручного запуска относительно
создания, опубликованный соседний стрим, незавершённая загрузка, повторы, права,
рестарт API и удаление стрима. Внешний HTTP-guard только запрещает модельные запросы.

Живая приёмка расширяет сценарий №11, чтобы два реальных батча проверяли и
сравнение, и историю. Используются настоящие HTTP API/worker, `call_002.mp3` и
`call_003.mp3` либо `VOX_LIVE_AUDIO`/`VOX_LIVE_AUDIO_SECOND`, настроенные Whisper/LLM.
История сверяется с опубликованными сводками и подробными отчётами, проверяются
пустая история до публикации, права, повторы, очистка аудио, рестарт и удаление.
API работает с недоступными модельными URL; аналитический worker использует
настоящие сервисы. Входы, БД и ключи тестового доступа изолированы от рабочих данных.

Приёмка 2026-10-08: живая история/сравнение прошли за 71.344 с с Whisper
`whisper-large-v3` и LLM `kimi-k2.7-code`, два успешных результата. Три обычных
REST-теста №12 прошли; полная suite — 75 прошли, 9 opt-in пропущены; контекст —
3 прошли, 1 opt-in пропущен. compileall и pip check успешны. Живая проверка
выполнялась отдельно, её пропуск в обычной suite не означает отсутствие приёмки.

Итоговое независимое ревью относительно подтверждённого `f080fa3`: Standards —
0 замечаний; Spec — 0 замечаний. №12 завершён; совместимость снимка истории с
публикацией и удалением стрима №13 подтверждена проверкой реализации и приёмкой.
