# Vox AI: требования и проектирование backend

Обновление 2026-10-09: пользователь выбрал исключать отключённые критерии из
итоговой оценки. Новый стрим содержит непустой выбранный набор из 11 доступных;
максимум равен размеру набора. Это заменяет прежнее правило постоянных 11 критериев
и баллов ниже. Старые снимки и результаты сохраняются. См. docs/adr/0005-selected-stream-criteria.md.

Статус: обсуждение, спецификация не утверждена.

## Согласованные исходные требования

- Vox AI анализирует звонки колл-центра и оценивает работу сотрудника.
- На вход поступает запись звонка.
- В первой версии поддерживаются звонки с двумя участниками: одним сотрудником и одним клиентом.
- Заказчики массово загружают аудиофайлы через API.
- Для массовой загрузки через API заказчики используют отдельные API-ключи; backend определяет организацию по ключу.
- Через UI пользователь может загрузить ZIP-архив без пароля, содержащий отдельные аудиозаписи; архив принимает backend через REST API. Это единственный поддерживаемый формат архива в первой версии.
- Заказчик — отдельная организация. Каждый заказчик имеет доступ только к собственным записям, сотрудникам и отчётам.
- В тестовой версии у пользователей заказчика одна роль: загрузка записей, выбор готового стрима и просмотр всех отчётов своей организации.
- В тестовой версии пользовательские учётные записи не предусмотрены. Запросы из UI используют тот же API-ключ заказчика, что и интеграции.
- Система получает транскрипцию с разделением реплик сотрудника и клиента.
- От сервиса транскрибации требуется для каждой реплики текст, время начала и окончания в записи и идентификатор говорящего.
- Обработка аудиофайла выполняется стримом: транскрибация через Whisper → обработка транскрипции на стороне Vox AI → анализ полученных результатов с помощью LLM.
- Whisper и LLM используются как готовые сервисы с API. Backend передаёт им данные, получает результаты и управляет процессом обработки; развёртывание моделей не входит в согласованный объём backend.
- Стрим настраивается под заказчика; у одной организации может быть несколько стримов.
- В тестовой версии стримы создаёт и настраивает команда Vox AI; заказчики выбирают готовый стрим при загрузке.
- Стрим неизменяем в рамках его идентификатора. Любое изменение стрима, включая параметры и содержимое связанных словарей и базы знаний, означает новый идентификатор; результаты предыдущих батчей остаются связаны с исходным стримом.
- Стрим для обработки выбирается явно: через API передаётся идентификатор стрима, при загрузке архива через UI пользователь выбирает стрим.
- Батч соответствует одной загрузке: одному архиву через UI либо одной явно сформированной группе файлов через API. Батч относится к одному заказчику и одному выбранному стриму.
- Текущий ожидаемый объём тестового батча — около 300 звонков. Объём будет меняться; число 300 является ориентиром нагрузки, а не жёстким лимитом приёма файлов.
- Обычная длительность звонка — около 5 минут. Ориентировочный батч из 300 таких звонков содержит 25 часов аудио; это объём входного материала, а не оценка времени обработки.
- В тестовой версии измеряется фактическое время обработки батчей; жёсткий срок готовности отчёта не установлен.
- Через API заказчик создаёт батч с выбранным стримом, добавляет файлы несколькими запросами и явно завершает загрузку. После завершения загрузки батч готов к ручному запуску командой Vox AI.
- При API-загрузке отказ по одному файлу не препятствует приёму остальных. Завершить загрузку батча можно только при наличии хотя бы одной принятой записи.
- Интеграция заказчика или frontend создаёт идентификатор загрузки и сохраняет его при повторах после сбоя. Новый идентификатор означает независимую загрузку и новый батч.
- Внутри одного батча файлы с одинаковым содержимым соответствуют одной записи. Повторная загрузка такого файла связывается с существующей записью. В другой батч этот файл можно загрузить для нового анализа.
- При загрузке архива через UI backend автоматически завершает загрузку батча после успешной распаковки и приёма хотя бы одной записи. Затем батч ожидает ручного запуска командой Vox AI.
- Если ZIP распаковывается, но отдельные файлы повреждены или имеют неподдерживаемый формат, корректные записи принимаются в батч, а по проблемным файлам показываются ошибки загрузки.
- Если из архива не принято ни одной записи, загрузка считается неуспешной, причины ошибок показываются пользователю, а батч недоступен для запуска обработки.
- В отчёте количество записей батча включает только принятые записи. Непринятые файлы учитываются отдельным счётчиком ошибок загрузки: например, из 100 переданных файлов 10 отклонены — в батче 90 записей и отдельно 10 ошибок загрузки.
- После завершения загрузки состав батча неизменяем: добавление и удаление записей из его состава запрещены. Дополнительные файлы загружаются в новый батч.
- Для этапов Whisper и LLM предусмотрены редактируемые промпты, для обработки транскрипции — включаемые опции и словари.
- На третьем этапе к запросу LLM прикрепляется база знаний, на которую модель может опираться при оценке.
- Записи могут поступать в течение дня. Ночное использование ресурсов Whisper и LLM — ограничение целевого режима, которое пока не применяется к тестовой версии.
- Сейчас разрабатывается тестовая версия: все данные хранятся локально на компьютере, без отдельного сервиса файлового хранения.
- Для входных батчей используется внутренняя локальная директория загрузок API/UI. После успешного сохранения результатов в БД входные файлы сразу удаляются. При ошибке батча входы сохраняются до восстановления. Самостоятельного канала ручного помещения батчей в директорию нет.
- Идентификатор сотрудника и дата звонка необязательны. Продуктовые лимиты количества файлов, размеров аудио/архива, длительности звонка и whitelist аудиорасширений пока не устанавливаются; ZIP без пароля остаётся согласованным форматом архива.
- Отчёты предоставляются через REST API; файловая выгрузка в тестовую версию не входит. Отзыв/замена ключей и отключение старых стримов для новых загрузок также не входят.
- Автоматического удаления данных БД нет. Данные звонков, результаты и отчёты сохраняются до удаления своего стрима и удаляются вместе с ним.
- В тестовой версии обработка запускается вручную в любое время суток.
- Ручной запуск обработки батчей в тестовой версии выполняет команда Vox AI.
- Команда Vox AI управляет стримами и запускает батчи через REST API с отдельным административным API-ключом.
- Обработка батча выполняется в фоне: REST API подтверждает принятие запуска, не ожидая окончания анализа. Статус батча и готовый итоговый отчёт доступны отдельными запросами.
- Согласованы статусы батча: «загружается», «готов к запуску», «в очереди», «обрабатывается», «завершён», «ошибка загрузки» и «ошибка обработки батча». Ошибки отдельных записей показываются в отчёте завершённого батча.
- Повторный запрос запуска батча в очереди, в обработке или завершённого возвращает текущий статус без создания новой задачи и повторного анализа.
- Для тестовой версии используется общая очередь батчей всех заказчиков по времени принятия ручного запуска: раньше запущенный батч раньше начинает обработку.
- После обработки батча данные о звонках сохраняются в общей БД backend с привязкой к заказчику, стриму и исходному батчу. История результатов стрима позволяет сравнивать показатели разных батчей, обработанных в рамках одного стрима.
- В первой версии через REST API можно сравнить несколько выбранных завершённых батчей одного стрима по показателям каждого батча: счётчики записей и ошибок, средний итоговый балл, средние оценки 11 критериев, количество и доля критических нарушений.
- Аналитические результаты сохраняются в БД только после обработки батча; сохранение готового результата каждого звонка сразу после его обработки не принято. Повтор той же загрузки после сбоя защищается от повторной записи уже сохранённых результатов в БД. Независимая загрузка того же файла в новый батч допускает новый анализ.
- Сохранение результатов батча в БД выполняется по правилу «всё или ничего»: либо записан весь набор, либо при ошибке сохранения ни один новый результат этого батча не остаётся в БД.
- После повторной загрузки с прежним идентификатором батч со статусом «ошибка обработки батча» возвращается в «готов к запуску». Команда Vox AI запускает его вручную; обработка повторяется для всего батча.
- После перезапуска backend сохраняются очередь и её порядок. Ранее запущенные батчи, обработка которых ещё не началась, продолжаются автоматически. Прерванный батч получает статус «ошибка обработки батча» и восстанавливается повторной загрузкой с прежним идентификатором и ручным запуском.
- В тестовой версии во всей системе одновременно обрабатывается только один звонок. Остальные записи ожидают своей очереди; приём файлов и получение статусов и отчётов остаются доступными во время анализа.
- Команда Vox AI создаёт организации-заказчиков и выдаёт их API-ключи через административный REST API.
- В тестовой версии команда Vox AI имеет доступ к аудиозаписям и отчётам всех заказчиков через административный ключ.
- В тестовой версии не предусмотрен ручной повтор обработки записей с ошибками без повторной загрузки файлов.
- Результат LLM имеет общий для всех стримов формат: список критериев, у каждого — идентификатор, оценка и пояснение. Набор критериев определяется стримом.
- Допустимые значения оценки критерия: 0 — не выполнен, 0.5 — выполнен частично, 1 — выполнен полностью.
- Критерий «Критическое нарушение» имеет бинарную оценку: 0 — нарушение есть, 1 — нарушений нет.
- Каждый звонок оценивается по 11 критериям. Состав критериев фиксирован для стрима; каждый результат содержит все 11 критериев. Неприменимый к разговору критерий получает 1 по умолчанию с явным указанием неприменимости в пояснении.
- Обычная итоговая оценка звонка — сумма оценок 11 критериев с максимумом 11; максимальный результат отображается как «11 из 11». При критическом нарушении итог обнуляется, если в стриме включён соответствующий чекбокс.
- В настройках стрима предусмотрен чекбокс «При критическом нарушении обнулять оценку всего звонка», включённый по умолчанию.
- Исходный набор 11 критериев первой версии подтверждён по списку существующего прототипа; названия перечислены в разделе результата третьего этапа.
- В первой версии обязательны два уровня отчётности: подробный результат по каждому звонку и сводный отчёт по батчу.
- Сводный отчёт по батчу формируется на backend из результатов отдельных звонков, без дополнительного запроса к LLM.
- Сводный отчёт батча предоставляется только после завершения обработки всех его записей; промежуточная сводка не предоставляется.
- В первой версии система формирует отчёт для руководителя. Обсуждение с сотрудником происходит вне Vox AI; учёт обратной связи внутри системы не входит в первую версию.
- Backend и frontend находятся в отдельных репозиториях и взаимодействуют по REST API.
- В этой работе проектируем только backend. До согласования требований код не пишем.
- Принятые решения фиксируются в документации. По последней просьбе пользователя оставшиеся вопросы собраны единым списком в [вопросах для завершения проектирования](questions.md).
- Дальнейшие решения об обработке звонков внутри стрима берутся из реализации этого репозитория, без дополнительных вопросов пользователю об алгоритмах. Порядок обработки, метрики, разметка ролей, правила критериев и формат результата описаны в [обработке звонка](../../docs/call-processing.md). Ранее согласованные требования сохраняются; отличия прототипа от них отмечены отдельно.

## Бизнес-процесс: известная часть

Запись звонка → выполнение стрима (Whisper → обработка транскрипции в Vox AI → LLM) → составление отчёта → изучение отчёта руководителем → обратная связь сотруднику.

Основной пользователь результата — руководитель. Система собирает метрики на основе звонка и составляет отчёт; руководитель изучает отчёт и даёт обратную связь сотруднику.

Записи поступают от заказчиков через API либо в архиве, загруженном через UI, в том числе днём. В тестовой версии записи сохраняются локально на компьютере до обработки; обработка запускается вручную в любое время суток. Метрики и результат отдельного звонка принимаются из реализации репозитория, показатели сводного отчёта батча перечислены ниже.

## Границы первой версии

- Vox AI получает запись, анализирует звонок и формирует отчёт для руководителя.
- Целевой сценарий первой версии — разговор одного сотрудника с одним клиентом. Разметка говорящих и резервное поведение берутся из реализации репозитория, описанной в [call-processing.md](../../docs/call-processing.md).
- Изучение отчёта руководителем — предусмотренное использование результата системы.
- Обсуждение результатов с сотрудником происходит вне Vox AI. Хранение обратной связи и сопровождение этого обсуждения не входят в первую версию.

## Получение записей

- **Массовая загрузка через API:** заказчик создаёт батч с выбранным стримом, добавляет аудиофайлы несколькими запросами и отдельной операцией явно завершает загрузку. Отказ по одному файлу не мешает принимать остальные. Завершение загрузки допускается только при наличии хотя бы одной принятой записи; после него батч готов к ручному запуску командой Vox AI. Детальные форматы запросов и сведения о каждом звонке пока не определены.
- **Загрузка архива через UI:** пользователь передаёт ZIP-архив без пароля с отдельными аудиозаписями; один архив формирует один батч. После успешной распаковки архива и приёма хотя бы одной записи backend автоматически завершает загрузку батча. Батч ожидает ручного запуска командой Vox AI. Если ни одна запись не принята, загрузка считается неуспешной и запуск недоступен.
- **Выбор стрима:** при загрузке через API заказчик передаёт идентификатор стрима; при загрузке архива через UI пользователь выбирает стрим, и frontend передаёт этот выбор в backend.
- Выбранный стрим должен принадлежать тому же заказчику, что и загружаемые записи.
- Продуктовых лимитов количества файлов, размеров и длительности аудио и whitelist аудиорасширений пока нет. Фактическая поддержка аудио определяется сервисом транскрибации. В первой версии через UI принимаются только ZIP-архивы без пароля; при ошибках отдельных файлов допускается частичный приём архива.
- В тестовой версии после загрузки записи ожидают ручного запуска обработки, доступного в любое время суток.
- Ошибка обработки отдельного аудиофайла не останавливает обработку остальных записей батча.

### Батч

- Один батч — записи, переданные в рамках одной загрузки.
- Батч принадлежит одному заказчику и связан с одним выбранным стримом; все его записи обрабатываются по этому стриму.
- Через UI батч формируется из одного загруженного архива. Через API заказчик явно формирует группу файлов, составляющих батч.
- Результаты записей группируются по батчам для последующего анализа и сравнения в контексте стрима.
- Порядок загрузки через API согласован: создание батча с выбранным стримом → добавление файлов несколькими запросами → явное завершение загрузки → готовность к ручному запуску командой Vox AI. Отказ по отдельному файлу не мешает принимать остальные; для завершения загрузки нужна хотя бы одна принятая запись. Детальные форматы запросов пока не определены. Ручной запуск выполняется для батча; обработка идёт в фоне.
- Завершение загрузки фиксирует состав батча. После него нельзя добавлять или удалять записи из состава; дополнительные файлы относятся к новому батчу. Так сохраняется группа записей, по которой формируется итоговый отчёт.

### Статусы и переходы батча

| Статус | Значение |
| --- | --- |
| Загружается | Батч формируется: принимаются файлы через API либо импортируется архив из UI. Запуск обработки недоступен. |
| Готов к запуску | Загрузка завершена, принята хотя бы одна запись, состав батча зафиксирован. Батч ожидает ручного запуска командой Vox AI. |
| В очереди | Ручной запуск принят; батч ожидает начала фоновой обработки. |
| Обрабатывается | Выполняется обработка записей батча. |
| Завершён | Все принятые записи завершились успешно либо ошибкой обработки, результаты батча сохранены целиком; итоговый отчёт доступен. |
| Ошибка загрузки | Загрузка архива неуспешна; причины доступны пользователю, запуск обработки недоступен. |
| Ошибка обработки батча | Сбой прервал обработку всего батча либо сохранение результатов в БД завершилось ошибкой. Батч не завершён; итоговый отчёт не опубликован. |

Основной путь: загружается → готов к запуску → в очереди → обрабатывается → завершён. Ручной запрос команды Vox AI переводит готовый батч в очередь.

Ошибка завершения пустого API-батча не делает его готовым к запуску: он остаётся в состоянии загрузки. При неуспешной загрузке архива без принятых записей используется статус «ошибка загрузки».

Ошибки отдельных файлов при частичном приёме не означают ошибку загрузки всего батча, если приняты корректные записи и загрузка завершена. Ошибки отдельных записей при анализе показываются в отчёте завершённого батча, включая случай, когда все принятые записи завершились ошибкой обработки; в этом случае оценки обозначаются как «нет данных».

Если сбой прерывает обработку всего батча или сохранение результатов завершается ошибкой, батч получает статус «ошибка обработки батча». При ошибке сохранения действует правило «всё или ничего». Повторная загрузка с прежним идентификатором возвращает ошибочный батч в «готов к запуску»; после этого команда Vox AI запускает его вручную для обработки всего батча заново.

Машинное представление статусов в REST API ещё предстоит определить. Поведение после перезапуска описано в разделе фонового выполнения.

### Повторные запросы запуска

- Первый запрос команды Vox AI для батча со статусом «готов к запуску» переводит его в очередь для фоновой обработки.
- Если батч уже имеет статус «в очереди», «обрабатывается» или «завершён», повторный запрос запуска возвращает его текущий статус. Новая задача обработки не создаётся, повторный анализ не выполняется.
- Повторный запрос не меняет результаты уже завершённого батча. Для нового анализа файл может быть загружен в другой батч согласно правилу повторной загрузки.
- Батч со статусом «загружается» или «ошибка загрузки» недоступен для запуска, как и ранее согласовано.

### Восстановление ошибочного батча

- Восстановление применяется к батчу со статусом «ошибка обработки батча».
- Заказчик повторяет загрузку, сохраняя прежний идентификатор загрузки. После повторного приёма исходных записей тот же батч возвращается в статус «готов к запуску».
- Состав исходного батча и выбранный стрим сохраняются. Восстановление не создаёт независимый новый батч.
- Команда Vox AI запускает готовый батч вручную. Обработка выполняется заново для всего батча; автоматический запуск по факту повторной загрузки не применяется.
- Сохранение новых результатов после обработки остаётся целостным, с защитой от повторной записи по идентификатору исходной загрузки.
- Батчи в очереди, в обработке и завершённые по-прежнему возвращают текущий статус при повторном запросе запуска, без нового анализа.

### Порядок очереди батчей

- Батчи всех заказчиков после принятия ручного запуска попадают в общую очередь.
- Начало обработки следует порядку принятия запросов ручного запуска: ранее запущенный батч начинает обработку раньше позднее запущенного.
- Порядок определяется ручным запуском, а не временем создания батча или загрузки файлов.
- Повторный запрос запуска возвращает текущий статус и сохраняет первоначальное место батча в очереди.
- В тестовой версии одновременно выполняется обработка только одной записи звонка во всей системе, независимо от заказчика и стрима. Остальные записи ожидают своей очереди.
- Ограничение применяется к выполнению стрима; приём загрузок и REST-запросы статусов и отчётов остаются доступными во время обработки.
- Очередь и её порядок сохраняются после перезапуска backend; ещё не начатые батчи с принятым ручным запуском продолжаются автоматически. Технический механизм выполнения и хранения очереди ещё предстоит определить.

### Повторная загрузка и дубликаты

- Файлы с одинаковым содержимым внутри одного батча соответствуют одной записи звонка. Повторная загрузка связывается с уже созданной записью и не создаёт дополнительную запись.
- Правило относится к содержимому файла; разные имена файлов с одинаковым содержимым не делают их разными записями внутри батча.
- Повторная загрузка, связанная с существующей записью, не считается ошибкой загрузки и не увеличивает количество записей в отчёте.
- В другом батче файл с тем же содержимым может быть принят как отдельная запись для нового анализа по стриму этого батча.
- При повторе той же загрузки после сбоя уже сохранённые обработанные записи не должны повторно попадать в БД. Это защита от дублей при восстановлении исходной загрузки; независимая загрузка того же файла в новый батч допускает новый анализ и его отдельный результат.
- Для идентификации исходной загрузки используется идентификатор загрузки, создаваемый интеграцией заказчика или frontend. Он сохраняется при повторах после сбоя; новый идентификатор означает независимую загрузку и новый батч.
- Повтор с тем же идентификатором относится к исходной загрузке и не должен создавать дубли её уже сохранённых результатов. Конкретный механизм защиты в БД и детальный REST-контракт ещё предстоит определить.
- Неизменяемость состава завершённого батча сохраняется: новые записи в него не добавляются.
- Детальный формат ответа на повторную загрузку и поведение повторных запросов завершения загрузки ещё предстоит определить в REST-контракте. Идентификатор загрузки различает повтор исходной загрузки и независимую новую загрузку; повторный запрос запуска для батча в очереди, обработке или завершённого возвращает текущий статус без нового анализа.

### Формирование батча через API

1. Заказчик создаёт батч, указывая идентификатор стрима своей организации.
2. Заказчик загружает аудиофайлы в созданный батч несколькими запросами. Отказ по одному файлу не препятствует приёму остальных; по проблемному файлу возвращается ошибка загрузки.
3. После передачи файлов заказчик явно завершает загрузку батча отдельной операцией API. Завершение допускается, если принята хотя бы одна запись.
4. Батч становится готовым к ручному запуску командой Vox AI; завершение загрузки само по себе не запускает анализ.

До явного завершения API-загрузки батч имеет статус «загружается» и не готов к запуску. Если ни одна запись не принята, завершение загрузки отклоняется и статус сохраняется.

### Формирование батча из архива через UI

1. Пользователь выбирает готовый стрим своей организации и загружает ZIP-архив аудиозаписей без пароля через frontend; frontend передаёт архив и выбор стрима в REST API backend.
2. Backend распаковывает архив и принимает корректные записи в один батч выбранного стрима. Повреждённые файлы и файлы неподдерживаемого формата не принимаются; для них показываются ошибки загрузки.
3. После успешной распаковки и приёма хотя бы одной записи backend автоматически завершает загрузку батча, фиксируя его состав. Дополнительное действие пользователя для завершения загрузки не требуется.
4. Батч ожидает ручного запуска обработки командой Vox AI.

В первой версии поддерживается только ZIP без пароля. Ошибки отдельных файлов в распакованном архиве не препятствуют приёму корректных записей. Пользователь получает сведения о проблемных файлах и причинах отказа.

Если ни один файл из архива не удалось принять, загрузка считается неуспешной. Пользователю показываются причины ошибок; батч не становится готовым к обработке и его нельзя запустить.

Непринятые файлы учитываются отдельным счётчиком ошибок загрузки в отчёте. В количество записей батча входят только принятые записи.

Продуктовые лимиты размера и количества файлов не устанавливаются. Структура импорта подпапок, проверки файлов и обработка нераспаковываемого архива предложены в итоговом техническом проекте.

### Фоновое выполнение батча

- Команда Vox AI запрашивает запуск батча через административный REST API.
- API возвращает подтверждение принятия запуска, не ожидая выполнения стрима для всех записей. Это подтверждение не означает, что анализ уже завершён.
- Backend выполняет обработку батча в фоне. Алгоритмы обработки отдельных звонков сохраняются по реализации репозитория.
- Статус батча получается отдельным REST-запросом; итоговый сводный отчёт получается отдельным запросом после завершения обработки всех записей, включая завершившиеся ошибкой.
- После перезапуска backend очередь сохраняется вместе с порядком принятия ручного запуска. Батчи, уже поставленные в очередь, но ещё не начатые, продолжают обработку автоматически.
- Батч, обработка которого была прервана, получает статус «ошибка обработки батча» и восстанавливается по согласованному правилу: повторная загрузка с прежним идентификатором → готовность к запуску → ручной запуск всей обработки заново.
- Готовые батчи, для которых ручной запуск ещё не был принят, продолжают ожидать команды Vox AI. Завершённые батчи и сохранённые результаты сохраняются.
- Состояния загрузки, запуска и очереди должны переживать перезапуск. Это не меняет правило сохранения аналитических результатов только после обработки батча. Технический механизм фонового выполнения и хранения очереди ещё предстоит определить.

### Необязательные сведения о звонке

- Заказчик может передать идентификатор сотрудника из своей системы и дату звонка; оба поля необязательны в тестовой версии.
- Отсутствие этих сведений не препятствует приёму и анализу записи. Имя входного файла сохраняется как метаданные.
- Идентификатор сотрудника не равен идентификатору говорящего Whisper. Справочник сотрудников и автоматическое установление личности по голосу не входят в первую версию.
- Конкретные поля и передача метаданных в API/архиве предложены в REST-контракте итогового проекта.

## Время обработки и ограничения тестовой версии

### Ожидаемая нагрузка

- Сейчас в одном батче ожидается около 300 звонков.
- Обычная длительность одной записи — около 5 минут; это не максимальная допустимая длительность.
- При этих ориентирах батч содержит около 1500 минут, или 25 часов аудио. Фактическое время выполнения Whisper, LLM и обработки батча пока не измерено.
- Пользователь планирует менять объём батчей; число 300 не устанавливает фиксированный максимум.
- В тестовой версии сначала измеряется фактическое время обработки батчей. Жёсткий срок готовности отчёта не установлен; фактическая производительность пока не измерена.
- Для измерения фиксируются начало и окончание обработки батча. Ожидание ручного запуска и очереди отличается от времени выполнения обработки; детальное представление временных показателей в REST API ещё не выбрано.
- Продуктовые лимиты количества файлов, размеров файлов/архивов и длительности звонка пока не устанавливаются. Суточный объём не задан; производительность измеряется на фактических тестах.
- Ранее принятое ограничение тестового режима сохраняется: во всей системе одновременно обрабатывается один звонок.

### Режим обработки и хранение

- Приём записей возможен в течение дня.
- Для тестовой версии время суток не ограничивает использование Whisper и LLM.
- Для целевого ночного режима конкретные часы, часовой пояс и поведение незавершённых задач при окончании ночного окна пока не определены; эти вопросы отложены за пределы текущего тестового режима.
- В тестовой версии выбран ручной запуск обработки. Автоматический запуск по расписанию пока не входит в согласованный объём тестовой версии.
- Ручной запуск обработки батчей выполняет команда Vox AI через административный REST API; обработка выполняется в фоне, статус и готовый отчёт доступны отдельными запросами. Запущенные батчи всех заказчиков входят в общую очередь по времени принятия ручного запуска.
- В тестовой версии все данные хранятся локально на компьютере. Отдельный сервис файлового хранения не используется.
- Загруженные аудиозаписи и архивы сохраняются локально, чтобы записи оставались доступны до ручного запуска обработки.
- Локальное хранение также применяется к настройкам стримов, словарям, базам знаний, сведениям о звонках и результатам обработки. Данные звонков сохраняются в общей БД backend с привязкой к заказчику, стриму и батчу; в тестовой версии БД находится на компьютере. Конкретная СУБД, структура таблиц и формат остальных локальных данных пока не определены.
- Входная директория используется backend для загрузок API/UI. После успешной фиксации результатов батча входные файлы сразу удаляются; при ошибке всего батча сохраняются до восстановления. Завершённый батч с ошибками отдельных записей также очищается после сохранения его результатов.
- История результатов и транскрипций не удаляется автоматически. Удаление стрима удаляет его данные в общей БД, включая связанные батчи, записи, результаты и отчёты. Данные других стримов сохраняются.

## Заказчики и принадлежность данных

- В системе обслуживаются отдельные организации-заказчики.
- Записи звонков, батчи, сотрудники, отчёты и стримы принадлежат конкретному заказчику.
- Заказчик не имеет доступа к данным других заказчиков. Правило действует при загрузке через API, загрузке архивов через UI и получении результатов.
- Клиент — участник звонка; заказчик — организация, использующая Vox AI. Эти понятия не взаимозаменяемы.
- Ключ заказчика ограничивает доступ данными его организации. Отдельный административный ключ команды Vox AI разрешает просмотр аудиозаписей и отчётов всех заказчиков в тестовой версии.
- Техническая изоляция данных по ключу заказчика, проверки владельца в REST и связей в общей БД предложены в [проекте](../../docs/backend-design.md) и [модели данных](../../docs/data-model.md).

### Пользователь заказчика

- В тестовой версии предусмотрена одна роль пользователя заказчика.
- Пользователь может загружать записи, выбирать готовый стрим своей организации и просматривать все отчёты этой организации.
- Разделение доступа к отчётам внутри организации в тестовую версию не входит.
- Создание и настройку стримов и ручной запуск обработки выполняет команда Vox AI.
- В тестовой версии пользовательских учётных записей и входа по логину и паролю нет.
- Права пользователя описывают доступные действия представителя заказчика, а не отдельную учётную запись.
- Запросы из UI используют API-ключ заказчика. Backend определяет организацию по этому ключу и предоставляет доступ к загрузке записей, выбору готового стрима и отчётам своей организации.

### Авторизация интеграций заказчика

- Для массовой загрузки через API у каждого заказчика есть отдельный API-ключ, привязанный к его организации.
- Backend определяет организацию по API-ключу. Выбираемый стрим и создаваемый батч должны принадлежать этой организации.
- Один и тот же ключ используется для интеграций и UI. Он разрешает загрузку записей, выбор готового стрима и просмотр отчётов своей организации.
- Для команды Vox AI используется отдельный административный API-ключ. Он разрешает через REST API создание и настройку стримов и ручной запуск обработки батчей.
- API-ключ заказчика предоставляет права пользователя заказчика; административные операции выполняются с отдельным ключом команды Vox AI.
- Административный ключ также разрешает просмотр аудиозаписей и отчётов всех заказчиков в тестовой версии.
- Организации-заказчиков создаёт команда Vox AI через административный REST API; выдача ключей заказчикам также выполняется через этот API.
- Отзыв/замена ключей не входят в тестовую версию. Начальная настройка административного ключа предложена в техническом проекте; удаление заказчиков в API не предусматривается.

### Управление стримами

- В тестовой версии создание и настройка стримов выполняются командой Vox AI.
- Заказчик выбирает готовый стрим своей организации при загрузке записей.
- Команда Vox AI также выполняет ручной запуск обработки батчей в тестовой версии.
- Настройка изменённого стрима командой Vox AI приводит к новому идентификатору; исторические стримы и их результаты сохраняются.
- Управление стримами и ручной запуск батчей выполняются через REST API с административным ключом команды Vox AI.
- Команда Vox AI может просматривать аудиозаписи и отчёты всех заказчиков в тестовой версии.
- Команда Vox AI также создаёт организации-заказчиков и выдаёт им API-ключи через административный REST API.
- Отзыв/замена ключей и отключение старого стрима для новых загрузок не входят в тестовую версию. Удаление стрима удаляет и его историю; технический порядок удаления предложен в итоговом проекте.

## Стрим и этапы обработки

Стрим — настраиваемая последовательность обработки аудиофайла. В одной организации может быть несколько стримов с различными настройками.

По указанию пользователя от 2026-10-05 алгоритмы внутри стрима принимаются из существующего кода. Подробная последовательность и ссылки на исходники: [обработка звонка](../../docs/call-processing.md). Для обычного звонка с двумя говорящими сохраняются два отдельных логических запроса к LLM: назначение ролей перед расчётом метрик и оценка по критериям после него. Предложение объединить их не принято.

| Этап | Назначение | Настройки |
| --- | --- | --- |
| 1. Транскрибация | Получение через Whisper реплик с текстом, временем начала и окончания в записи и идентификатором говорящего | Редактируемый промпт Whisper |
| 2. Обработка транскрипции | Коррекция текста, назначение ролей отдельным запросом к LLM, сборка диалога и расчёт метрик в порядке существующего pipeline | Включаемые опции анализа темпа речи, поиска нежелательных слов и выражений, корректировки текста по словарю |
| 3. Анализ LLM | Анализ результатов предыдущих этапов с помощью LLM с опорой на прикреплённую базу знаний | Промпт LLM, закреплённое содержимое базы знаний и чекбокс обнуления итоговой оценки при критическом нарушении; изменение означает новый идентификатор стрима |

Опции второго этапа задаются чекбоксами:

- **Анализ темпа речи.** По существующему `acoustics.py` для каждой реплики число слов делится на её длительность с нижней границей 0.1 секунды; для каждой роли берётся среднее скоростей её реплик, в словах в секунду. Если опция отключена, критерий 2.2 «Темп разговора» получает 1 с пояснением «анализ темпа отключён».
- **Поиск нежелательных слов и выражений.** При включении опции обязателен словарь, на который опирается поиск.
- **Корректировка текста транскрипции по словарю.** При включении опции обязателен файл словаря для корректировки текста.

Словарь нежелательных слов и выражений и словарь корректировки текста имеют разные назначения. Коррекция берётся из алгоритма `WHISPER_FIXES`: пары ошибочного и правильного написания, применение от длинных ключей к коротким, регистрозависимый поиск с ограничением соседних букв. В прототипе маркеры грубости и неуверенности ищутся как подстроки в приведённом к нижнему регистру тексте сотрудника. Загрузка настраиваемых словарей из файлов и чекбоксы отсутствуют в прототипе и остаются согласованными расширениями; это отмечено в разделе отличий [обработки звонка](../../docs/call-processing.md).

Стрим выбирается явно при загрузке: по идентификатору через API либо пользователем через UI.

### Требования к транскрипции

- Ответ сервиса транскрибации содержит реплики с текстом, временем начала и окончания в записи и идентификатором говорящего, например SPEAKER_00.
- Идентификатор говорящего обозначает участника внутри конкретного звонка. Роли назначаются как в `assign_roles`: отдельный запрос к LLM по первым 15 репликам; выбранный говорящий становится сотрудником, остальные — клиентом.
- Требуемые данные используются для разделения ролей и анализа темпа речи.
- Разбор ответа и резервное поведение берутся из `transcriber.py`: временные границы приводятся к секундам, поддерживаются строка `transcription`, массив `segments` и ответ только с `text`. При одном говорящем роль сотрудника назначается без запроса; при ошибке разметки используется первый идентификатор после сортировки.
- Текстовый резервный ответ получает нулевые временные границы и одного говорящего. Это ограничение прототипа относительно ранее согласованного требования к полным данным реплик зафиксировано в [обработке звонка](../../docs/call-processing.md); оно не гарантирует качественную диаризацию или метрики времени.

### Третий этап: база знаний

- К запросу LLM вместе с результатами предыдущих этапов прикрепляется база знаний.
- LLM может ссылаться на базу знаний при оценке разговора.
- База знаний и словари второго этапа имеют разные назначения: база предоставляет справочные материалы для оценки, словари используются для поиска нежелательных выражений и корректировки текста.
- Чтение базы знаний берётся из `kb.py`: quoted-printable/UTF-8, извлечение заголовков и ячеек из HTML-представления, очистка пробелов. Это не универсальный загрузчик бинарных документов Word. В запрос LLM передаются первые 20 000 символов очищенного текста вместе с чек-листом, метриками и диалогом.
- Проверка базы знаний и пояснения следуют промпту `analyzer.py`: выявленные вопросы, корректность ответов и расхождения с полями вопроса, ответа сотрудника и сведений базы. Если в базе нет ответа, это отмечается. Отдельный поиск документов и формальные идентификаторы ссылок в реализации отсутствуют.
- Содержимое базы знаний закреплено за конкретным стримом. Изменение базы знаний означает новый идентификатор стрима; прежнее содержимое сохраняется в контексте исходного стрима.

### Результат третьего этапа

- Для всех стримов используется общий формат результата LLM — набор оценённых критериев. В реализации это объект `scores`, где ключ — идентификатор критерия, а значение содержит `score`, `max` и `reason`; внешний REST-контракт ещё проектируется.
- Каждый критерий содержит идентификатор, оценку и пояснение этой оценки.
- Набор из 11 критериев задаётся конкретным стримом и фиксирован для него. Исходные правила берутся из `CHECKLIST` в `checklist.py` и передаются в запрос оценки вместе с промптом.
- Каждый результат по звонку содержит полный набор из 11 критериев стрима, по одной оценке на каждый критерий.
- Идентификаторы критериев позволяют соотносить оценки отдельных звонков при формировании сводного отчёта по батчу и сравнении батчей одного стрима.
- Оценка критерия числовая; допустимые значения — 0, 0.5 и 1.
- Значение баллов: 0 — критерий не выполнен; 0.5 — выполнен частично; 1 — выполнен полностью.
- Для критерия 5.2 «Критическое нарушение» допустимы только 0 и 1: 0 — нарушение есть, 1 — нарушений нет. Значение 0.5 для этого критерия не используется.
- Если во втором этапе стрима отключён анализ темпа речи, критерий 2.2 «Темп разговора» получает 1 с пояснением «анализ темпа отключён». Критерий остаётся в полном наборе и участвует в исходной сумме оценок.
- Неприменимый к конкретному разговору критерий получает 1 по умолчанию. В пояснении оценки явно указывается, что критерий неприменим; он остаётся в полном наборе критериев результата.
- Отдельный статус «неприменим» не используется. Правило и причина зафиксированы в [ADR-0002](../../docs/adr/0002-inapplicable-criteria-score-one.md).
- Таким образом, оценка 1 может означать полное выполнение либо неприменимость; различие отражается в пояснении.
- Исходная сумма оценок звонка складывается из всех 11 оценок критериев. Каждый критерий даёт до 1 балла, максимальная сумма — 11.
- Представление итоговой оценки: «<сумма> из 11». Например, десять оценок 1 и одна 0.5 дают «10.5 из 11»; одиннадцать оценок 1 дают «11 из 11».
- Дополнительные поля берутся из `analyzer.py`: признак и описание критического нарушения, тональность обоих участников, уровень стресса сотрудника, нарушения этикета, проверка базы знаний и рекомендации. Pipeline добавляет обработанные реплики `_segments` и метрики `_metrics`.
- Пояснения, цитаты и резервное поведение следуют существующим промптам и нормализации: отсутствующий критерий дополняется оценкой 0 с техническим пояснением; итог пересчитывается на backend. Неприменимость критерия остаётся отдельным случаем с оценкой 1 по ADR-0002.
- Прототип не проверяет допустимую шкалу чисел и лишние идентификаторы критериев. Ранее согласованные ограничения — ровно 11 критериев и только допустимые оценки — сохраняются как требования к backend. Подробности результата и отличий описаны в [обработке звонка](../../docs/call-processing.md).

### Обнуление итоговой оценки при критическом нарушении

- В настройках стрима есть чекбокс «При критическом нарушении обнулять оценку всего звонка».
- Если чекбокс включён и критерий 5.2 «Критическое нарушение» получил 0, итоговая оценка звонка — «0 из 11».
- Если чекбокс выключен либо критического нарушения нет, итоговая оценка равна обычной сумме 11 оценок критериев.
- Исходные оценки всех критериев сохраняются для разбора звонка; при обнулении в отчёте указывается причина итоговой оценки 0.
- Значение чекбокса является частью неизменяемых настроек стрима; его изменение требует нового идентификатора стрима.
- При создании стрима чекбокс по умолчанию включён.
- Факт критического нарушения определяется оценкой 0 по критерию 5.2.
- Исходный перечень критических нарушений первой версии:
  - Неверная консультация или оформление.
  - Обман.
  - Дискредитация компании.
  - Обесценивающие высказывания.
  - Негативный отзыв о компании.
  - Оценочные комментарии о работе систем или сотрудников.

### Неизменяемость стрима и сравнение батчей

- Каждый идентификатор стрима соответствует неизменным настройкам и связанным материалам обработки.
- Любые изменения стрима означают новый идентификатор, включая изменения промптов, опций, содержимого словарей и базы знаний.
- Обновление словаря или базы знаний не должно скрыто менять поведение прежнего стрима; исходное содержимое сохраняется для интерпретации результатов его батчей.
- Батчи и их результаты связаны с конкретным идентификатором стрима. Изменение настроек не переводит уже принятые батчи на новый стрим.
- Исходные настройки стрима сохраняются для интерпретации результатов предыдущих батчей. Это позволяет сравнивать батчи, обработанные по одним и тем же правилам.
- Решение и его причина записаны в [ADR-0001](../../docs/adr/0001-immutable-streams.md).
- Независимый новый анализ того же файла в другом батче разрешён. Сравнение в первой версии выполняется между выбранными завершёнными батчами одного стрима.

### История результатов стрима

- После обработки батча данные о его звонках сохраняются в общей БД backend и пополняют историю результатов соответствующего стрима.
- Аналитические результаты записываются в БД только после обработки батча. Предложение сохранять каждый результат сразу после обработки звонка отклонено; момент сохранения результатов отличается от приёма входных файлов и ведения состояния загрузки.
- Сохранение результатов батча целостное, по правилу «всё или ничего»: сначала заканчивается обработка и собирается набор результатов, затем весь набор сохраняется в БД. Если сохранение завершается ошибкой, ни один новый результат этого батча не остаётся в БД.
- Батч становится завершённым и его итоговый отчёт доступен после успешной фиксации всего набора результатов. Ошибка отдельной записи, уже учтённая в итогах обработки, не равна ошибке сохранения батча.
- При ошибке на уровне батча и повторе той же загрузки уже сохранённые обработанные записи должны быть защищены от повторной записи в БД. Это правило действует и если сохранение уже состоялось, но клиент не получил подтверждение. Независимая новая загрузка того же файла в другой батч допускает новый анализ и отдельный результат с принадлежностью к новому батчу. Исходная загрузка определяется идентификатором, создаваемым интеграцией или frontend и сохраняемым при повторах. Техническая реализация целостного сохранения ещё не выбрана.
- Сохраняется принадлежность данных заказчику, неизменяемому идентификатору стрима и исходному батчу. Это позволяет выбирать результаты конкретного батча и сравнивать показатели разных батчей одного стрима.
- Изменение настроек создаёт новый стрим; исторические данные предыдущего стрима остаются связанными с его исходным идентификатором.
- Используется общая БД с привязкой данных к заказчику, стриму и батчу. «БД стрима» обозначает данные соответствующего стрима в этой общей БД. Права заказчика по-прежнему ограничены его организацией; административный доступ команды Vox AI сохраняется.
- Сравнение выбранных завершённых батчей одного стрима через REST API согласовано в разделе ниже. Детальная схема запроса и ответа ещё предстоит определить. После перезапуска очередь сохраняется, ещё не начатые батчи с принятым запуском продолжаются автоматически. Прерванный батч восстанавливается повторной загрузкой с прежним идентификатором и ручным запуском обработки всего батча. Сохранение аналитических результатов остаётся только после обработки батча.

### Сравнение батчей одного стрима

- Пользователь выбирает несколько завершённых батчей одного стрима; backend предоставляет показатели каждого выбранного батча через REST API.
- Все выбранные батчи принадлежат одному стриму и, соответственно, одному заказчику. Доступ определяется ранее согласованными правами заказчика и команды Vox AI.
- Для каждого батча возвращаются уже согласованные показатели: количество принятых записей, успешных записей, ошибок обработки и ошибок загрузки; средний итоговый балл из 11; средняя оценка каждого из 11 критериев; количество и доля критических нарушений.
- Показатели предоставляются отдельно по каждому батчу для сопоставления. Данные берутся из сохранённых результатов; правила расчёта и представление «нет данных» сохраняются.
- Детальная схема REST-запроса и ответа ещё не выбрана. Frontend представляет полученные показатели; разработка frontend остаётся вне текущего объёма.

Whisper и LLM — готовые сервисы с API, к которым обращается backend. Порядок операций, контракты вызова, текущие параметры и обработка ответа принимаются из реализации, описанной в [обработке звонка](../../docs/call-processing.md). Протокол загрузки батча и внешняя REST-оболочка вокруг этого процесса ещё проектируются. Перенос общих настроек прототипа в неизменяемые стримы и согласованные чекбоксы остаются расширениями.

## Ошибки обработки батча

- При API-загрузке ошибка приёма одного файла не препятствует приёму остальных. Завершение загрузки допускается только при наличии хотя бы одной принятой записи; непринятые файлы учитываются как ошибки загрузки.
- При загрузке распаковываемого ZIP-архива корректные записи принимаются в батч, а повреждённые файлы и файлы неподдерживаемого формата получают ошибки загрузки. Ошибки видны пользователю по соответствующим файлам.
- Если из архива не принято ни одной записи, загрузка неуспешна и запуск обработки батча запрещён; причины ошибок доступны пользователю.
- Непринятые файлы учитываются как ошибки загрузки отдельным счётчиком в отчёте. В число записей батча и ошибок обработки принятых записей они не входят.
- Если отдельную запись не удалось обработать, ошибка фиксируется для этой записи, а обработка остальных записей батча продолжается.
- Отчёт батча формируется по успешно обработанным звонкам; записи с ошибками учитываются отдельным счётчиком, их ошибки доступны отдельно.
- В тестовой версии ручной повтор обработки записей с ошибками без повторной загрузки файлов не предусмотрен.
- Резервное поведение внутри стрима наследуется из реализации. Отдельного прикладного цикла повторных попыток в ней нет; поведение используемого SDK сохраняется. Прерванный батч восстанавливается повторной загрузкой с прежним идентификатором и ручным запуском заново. Поведение при невозможности распаковки архива ещё предстоит согласовать.

## Два уровня отчётности

- **Отчёт по звонку:** подробные результаты анализа отдельной записи в контексте выбранного стрима.
- **Сводный отчёт по батчу:** результаты анализа группы записей одной загрузки; используется руководителем для изучения батча и сравнения с другими батчами того же стрима.
- Сводный отчёт формируется на backend из результатов отдельных звонков. Дополнительный запрос к LLM для общего анализа батча не выполняется.
- Оба уровня входят в первую версию.
- Согласованный набор показателей сводного отчёта по батчу:
  - Количество принятых записей без дубликатов внутри батча: всего, успешно обработано, с ошибками обработки.
  - Количество ошибок загрузки — непринятых файлов.
  - Средняя итоговая оценка успешно обработанных звонков, представленная из 11.
  - Средняя оценка каждого из 11 критериев.
  - Количество и доля звонков с критическими нарушениями.
- Средняя итоговая оценка рассчитывается по успешным результатам звонков и использует итог с учётом правила обнуления при критическом нарушении.
- Средняя оценка каждого критерия рассчитывается по успешно обработанным звонкам; исходные оценки критериев сохраняются даже при обнулении итоговой оценки звонка.
- Количество критических нарушений — количество успешно обработанных звонков с оценкой 0 по критерию 5.2. Доля критических нарушений рассчитывается относительно количества успешно обработанных звонков.
- Записи с ошибками не входят в расчёт средних и доли критических нарушений и не получают подставленных оценок; они учитываются отдельным счётчиком ошибок.
- Количество записей «всего» означает количество принятых записей батча. В итоговом отчёте оно равно сумме успешно обработанных записей и записей с ошибками обработки. Ошибки загрузки показываются отдельным счётчиком и не входят в эту сумму или расчёт средних оценок.
- Файлы с одинаковым содержимым внутри батча учитываются как одна запись: она обрабатывается и участвует в счётчиках и оценках один раз. Повторная загрузка, связанная с этой записью, не увеличивает счётчик ошибок загрузки.
- Пример: передано 100 файлов, 10 не принято — в батче 90 записей и отдельно 10 ошибок загрузки. Если из этих 90 записей 80 обработаны успешно, а 10 завершились ошибкой обработки, отчёт показывает 90 всего, 80 успешных, 10 ошибок обработки и 10 ошибок загрузки; средние оценки рассчитываются по 80 успешным звонкам.
- Сводный отчёт доступен только в итоговом виде после завершения обработки всех записей батча: каждая запись обработана успешно либо завершилась ошибкой. Промежуточный сводный отчёт не предоставляется.
- Если все записи батча завершились ошибкой, итоговый отчёт содержит счётчики записей и сведения об ошибках. Средняя итоговая оценка, средние оценки критериев и доля критических нарушений обозначаются как «нет данных»; они не подменяются нулевыми оценками.
- В [REST-контракте](../../docs/rest-api.md) предложены числовые показатели, null для отсутствующих средних/доли и округление средних до двух знаков; исходные оценки не округляются дополнительно.
- Отчёты выдаются через REST API. CSV/XLSX/PDF-выгрузки в тестовую версию не входят; frontend находится в отдельном репозитории. Конкретные схемы ответов предложены в итоговом REST-контракте.

- 2026-10-05: для загрузки через UI в первой версии принимаются только ZIP-архивы без пароля.
- 2026-10-05: если ZIP-архив распаковывается, но отдельные файлы повреждены или имеют неподдерживаемый формат, корректные записи принимаются в батч, а по проблемным файлам показываются ошибки загрузки. Поведение при отсутствии принятых записей и учёт непринятых файлов в сводных счётчиках пока не определены.
- 2026-10-05: если ни один файл из архива не удалось принять, загрузка считается неуспешной, пользователю показываются причины ошибок, а батч недоступен для запуска обработки. Автоматическое завершение UI-загрузки с готовностью к запуску требует хотя бы одной принятой записи.
- 2026-10-05: ошибки загрузки учитываются отдельным счётчиком в отчёте, а количество записей батча включает только принятые записи. Пример: 100 файлов, 10 не принято — 90 записей батча и отдельно 10 ошибок загрузки. Ошибки загрузки не увеличивают счётчик ошибок обработки и не участвуют в расчёте оценок.
- 2026-10-05: для API-загрузки принят тот же принцип частичного приёма: отказ по одному файлу не мешает принимать остальные. Завершить загрузку батча можно только при наличии хотя бы одной принятой записи.
- 2026-10-05: файлы с одинаковым содержимым внутри одного батча соответствуют одной записи; повторная загрузка связывается с существующей записью. Эта запись учитывается и обрабатывается один раз. В другой батч тот же файл можно загрузить для нового анализа.
- 2026-10-06: согласованы статусы батча: загружается → готов к запуску → в очереди → обрабатывается → завершён, а также ошибка загрузки для неуспешной загрузки архива. Ошибки отдельных записей показываются в отчёте завершённого батча; ранее согласованное правило «нет данных» сохраняется при ошибке обработки всех записей.
- 2026-10-06: повторный запрос запуска батча со статусом «в очереди», «обрабатывается» или «завершён» возвращает его текущий статус без создания новой задачи и запуска нового анализа. Уже полученные результаты сохраняются.
- 2026-10-06: принята общая очередь батчей всех заказчиков по времени принятия ручного запуска: раньше запущен — раньше начинается обработка. Ответ «lf» интерпретирован как «да», набранное в английской раскладке; это явно отмечено в сообщении пользователю.
- 2026-10-06: для тестовой версии принято ограничение параллельности — во всей системе одновременно обрабатывается один звонок, остальные записи ожидают своей очереди. Ограничение относится к обработке, а не к доступности REST API.
- 2026-10-06: после обработки батча данные о звонках попадают в «БД стрима», чтобы сравнивать показатели разных батчей одного стрима. Сохраняется связь с заказчиком, стримом и исходным батчем; физическая организация БД ещё не выбрана. На предыдущее предложение о восстановлении после перезапуска ответа не получено, оно остаётся открытым.
- 2026-10-06: выбрана общая БД backend с привязкой данных к заказчику, стриму и батчу. История каждого стрима хранится в общей БД; СУБД и структура таблиц ещё не выбраны.
- 2026-10-06: результаты сохраняются в БД только после обработки батча; предложение сохранять результат каждого звонка сразу после его обработки отклонено. При повторной загрузке после сбоя уже сохранённые обработанные записи не должны повторно попадать в БД. Различие между повтором после сбоя и ранее разрешённым независимым новым анализом в другом батче ещё требует уточнения.
- 2026-10-06: подтверждено разграничение: повтор той же загрузки после сбоя защищается от повторной записи уже сохранённых результатов в БД, а независимая загрузка того же файла в новый батч допускает новый анализ и отдельный результат. Идентификация исходной загрузки ещё не выбрана.
- 2026-10-06: принят идентификатор загрузки, создаваемый интеграцией заказчика или frontend и сохраняемый при повторах после сбоя. Новый идентификатор означает независимую загрузку и новый батч; повтор с прежним идентификатором относится к исходной загрузке и защищается от дублей результатов в БД.
- 2026-10-06: принято сохранение результатов батча в БД по правилу «всё или ничего»: либо фиксируется весь набор, либо при ошибке сохранения ни один новый результат этого батча не остаётся в БД. Защита от повторной записи по идентификатору исходной загрузки сохраняется.
- 2026-10-06: добавлен статус «ошибка обработки батча» для сбоя, прервавшего весь батч, или ошибки сохранения результатов. Ошибки отдельных звонков по-прежнему отражаются в отчёте завершённого батча; восстановление после сбоя всего батча ещё не согласовано.
- 2026-10-06: после повторной загрузки с прежним идентификатором ошибочный батч возвращается в «готов к запуску». Команда Vox AI вручную запускает обработку всего батча заново; сохраняются исходный батч, его состав и выбранный стрим, а защита от дублей результатов в БД действует по-прежнему.

Прерванный батч получает статус ошибки и требует повторной загрузки с прежним идентификатором и ручного запуска заново. Аналитические результаты по-прежнему сохраняются только после обработки батча.
