# 09: Восстановление прерванного батча

**What to build:** Заказчик повторяет исходные файлы ошибочного батча с прежним идентификатором, затем команда вручную запускает весь батч заново без дублей публикации.

**Blocked by:** 06 — Массовая API-загрузка с частичным приёмом; 08 — Устойчивая общая очередь и защита от повторного запуска.

Status: ready-for-human

- [x] После сбоя обработки всего батча или атомарной фиксации сохранить ошибочный статус, причину и входы без опубликованного частичного набора аналитики.
- [x] Восстановление сохраняет исходный батч, стрим и зафиксированный состав. Другой состав или стрим требует независимой загрузки с новым идентификатором.
- [x] Требовать повторный приём исходных файлов; сохранившиеся на диске файлы не разрешают обход этого правила. Повторы восстановительных запросов не сбрасывают достигнутый приём.
- [x] После полного повторного приёма батч готов к ручному запуску; автоматический запуск не выполняется. Новая попытка получает новое место FIFO.
- [x] Обработать весь батч заново реальными моделями, не используя незафиксированный аналитический прогресс предыдущей попытки.
- [x] При потере подтверждения успешной фиксации повторы возвращают сохранённые результаты без повторного анализа или второй публикации.
- [x] Проверить контролируемый локальный сбой фиксации и прерывание worker, восстановление через API и единственность опубликованного набора с реальными БД/файлами и моделями.

### 2026-10-07 — зависшие приёмы из №06

При реализации устойчивости учесть таблицу `active_uploads`: обычный запрос
очищает регистрацию в `finally`, но аварийное завершение API может оставить её
и блокировать `complete` кодом `upload_in_progress`. Восстановление должно
безопасно отличать живые приёмы других процессов от прерванных; безусловная
очистка регистраций при запуске нового экземпляра API небезопасна.
