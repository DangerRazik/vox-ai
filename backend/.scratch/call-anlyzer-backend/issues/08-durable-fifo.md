# 08: Устойчивая общая очередь и защита от повторного запуска

**What to build:** Запущенные батчи всех заказчиков выполняются по порядку принятия запуска; очередь переживает рестарт и не допускает параллельного анализа звонков.

**Blocked by:** 05 — Первый сквозной анализ батча из одного звонка.

Status: ready-for-human

- [x] Сохранять очередь и порядок до начала обработки; FIFO определяется принятым ручным запуском, не созданием батча.
- [x] Конкурирующие запуски одного батча создают одну задачу. Повтор для ожидающего, обрабатываемого или завершённого возвращает состояние без новой задачи, сдвига очереди и анализа.
- [x] Во всей системе один звонок обрабатывается за раз, включая попытку запуска второго worker; REST-чтение и загрузки остаются доступны.
- [x] После рестарта worker ранее запущенные, но не начатые батчи продолжаются в сохранённом порядке. Незавершённая обработка без публикации получает ошибку батча; входы сохраняются.
- [x] Перезапуск только API не объявляет ошибочным батч продолжающего работу worker. Уже опубликованные результаты не анализируются повторно.
- [x] Захват задания и переход в обработку атомарны; неуспешная попытка освобождает старое задание очереди.
- [x] Проверить FIFO нескольких организаций, конкурирующие запросы, второй worker и рестарт с реальной БД; выполняемая обработка использует реальные модели.

## Comments

### Реализация и приёмка — 2026-10-07

Продолжен существующий backend от `6de5b1d`, ветка `master`, исходный diff пуст.
Зависимость 05 подтверждена завершённой, backend не переинициализирован.
ffprobe 9.0.2 фактически запускается, установки не выполнялись.

Очередь хранится в SQLite `batch_queue`: уникальный батч, монотонный номер
принятого запуска, время принятия и захвата. Enqueue/status, claim/processing
и публикация/освобождение задания — отдельные короткие атомарные транзакции.
Модели выполняются вне HTTP-запроса и транзакции. Ошибка освобождает попытку;
повторные start не меняют FIFO. Worker держит существующий configured OS lock
и канонический lock рядом с БД, так что другой `VOX_WORKER_LOCK` не обходит
эксклюзивность. Recovery выполняется только после захвата обеих блокировок.

TDD: воспроизведены отсутствие FIFO, обход порядка через process, отсутствие
recovery и зависание legacy queued. 7 новых детерминированных тестов с реальной
временной SQLite: обратный порядок creation/start, 16 конкурентных start/claim,
откаты enqueue/claim посредством триггеров SQLite, освобождение после отказа,
сохранение входов, отсутствие recovery при инициализации API, legacy diagnosis.
Модельные ответы не подменялись; детерминированные ошибки происходят до моделей.

`RUN_LIVE_FIFO_TEST=1`: два успешных прогона, 48.871 с и после review-исправления
17.609 с. Отдельные настоящие HTTP API/worker, временные БД/материалы/входы,
`call_002.mp3`, действующие настройки Whisper/LLM без подмен. Две организации,
creation в обратном порядке запуска; 16 REST-start дают один 202 и пятнадцать
200. Второй worker с другим configured lock выходит с ошибкой, не восстанавливая
активный батч. Во время обработки доступен REST и `BEGIN IMMEDIATE`.
Прерванный worker оставляет неопубликованный processing; новый worker переводит
его в batch_failed/worker_interrupted, сохраняет вход и автоматически продолжает
два ожидающих батча в FIFO. API перезапускается до worker и во время его работы;
загрузка дополнительного батча проходит. Два реальных успешных результата имеют
11 критериев, сводки сверены с фактическими ответами. После рестарта worker
completed/start возвращает 200, отчёт неизменен, в БД ровно два результата,
очередь пуста; интервалы обработки батчей не перекрываются.

Code-review выполнен локально по двум осям Standards/Spec относительно `6de5b1d`
(инструмента sub-agents нет). Исправлено замечание Spec: queued старой версии
не имеет сохранённого порядка. Такой батч теперь явно получает
batch_failed/queue_order_unavailable с сохранением входов; порядок не выдумывается.
Документированы остановка старой версии перед обновлением и локальные пути БД.
Нерешённых блокирующих замечаний Standards/Spec нет.
