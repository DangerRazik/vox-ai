# Vox AI backend

REST API на FastAPI, постоянная SQLite и последовательный обработчик батчей.
Транскрибация выполняется через Whisper, распределение ролей и оценка — через LLM
с OpenAI-совместимым API. Frontend находится в отдельном соседнем репозитории.

## Подготовка окружения

Нужны Python 3.10+ и ffprobe (из FFmpeg) для проверки аудиофайлов.
Из корня этого репозитория в PowerShell:

```powershell
python -m venv .venv-backend
.\.venv-backend\Scripts\python.exe -m pip install -r requirements.txt
```

Создайте `.env` в корне backend. Пример структуры с заглушками:

```dotenv
WHISPER_API_KEY=<ключ сервиса транскрибации>
WHISPER_BASE_URL=https://your-provider.example/v1
WHISPER_MODEL=whisper-large-v3
GPL_API_KEY=<ключ сервиса LLM>
GPL_BASE_URL=https://your-provider.example/v1
GPL_MODEL=<модель LLM вашего провайдера>
VOX_ADMIN_API_KEY=<отдельный случайный ключ не короче 24 символов>
VOX_DATABASE_PATH=data/vox.sqlite3
VOX_MATERIALS_ROOT=data/streams
VOX_INPUTS_ROOT=data/inputs
VOX_WORKER_LOCK=data/worker.lock
VOX_FFPROBE_PATH=C:/tools/ffmpeg/bin/ffprobe.exe
```

Замените заглушки своими значениями. Модель и адрес зависят от провайдера.
Если ffprobe доступен в PATH, `VOX_FFPROBE_PATH` можно не задавать.
При необходимости исключить шлюз из системного прокси задайте `NO_PROXY`
с точным именем его хоста. `.env` не хранится в Git.

`VOX_ADMIN_API_KEY` — ключ команды Vox AI, а не ключ Whisper/LLM. Короткий ключ
не пройдёт проверку настроек. Случайный ключ можно сгенерировать локально:

```powershell
.\.venv-backend\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(32))"
```

Сохраните полученное значение в `.env`. После изменения `.env` перезапустите API
и обработчик. Ключи заказчиков создаются через административный API и выдаются
один раз; SQLite хранит их хеши.

## Запуск

Для локальной работы всего приложения из соседнего frontend:

```powershell
cd ../frontend
npm ci
npm start
```

Общий запуск поднимает API, обработчик и frontend. Подробнее —
[README frontend](../frontend/README.md).

Для отдельного запуска используйте два терминала, оба из корня backend.

API:

```powershell
.\.venv-backend\Scripts\python.exe -m uvicorn backend.api:create_app --factory --host 127.0.0.1 --port 8000
```

Обработчик:

```powershell
.\.venv-backend\Scripts\python.exe -m backend.worker
```

API принимает запросы и сохраняет задания; обработчик извлекает их из очереди
и вызывает модели. Без обработчика батч может быть принят и поставлен в очередь,
но анализ не начнётся. Оба процесса должны использовать одну БД и одни каталоги
материалов/аудио. При разных рабочих каталогах задайте абсолютные пути.
Для этой БД одновременно работает один worker; это обеспечивают блокировки.

Документация запущенного API: `http://127.0.0.1:8000/docs`.
Для production API и worker запускаются как постоянные службы; браузерные
запросы frontend `/api/v1` проксируются к backend `/v1` через HTTPS.
Защищённые запросы API используют `Authorization: Bearer <key>`.

## Цикл обработки

1. Команда создаёт заказчика и выдаёт ему ключ.
2. Команда создаёт неизменяемый стрим: настройки, база знаний, опциональные словари.
3. Заказчик загружает ZIP в стрим. Backend проверяет архив и аудио, фиксирует
   принятые файлы, дубликаты и ошибки. Название батча берётся из имени ZIP.
4. Команда вручную ставит готовый батч в очередь. Worker обрабатывает её по FIFO.
5. Для звонка выполняются транскрибация, разметка ролей, подготовка текста/метрик,
   проверка базы знаний и оценка LLM.
6. После обработки всего батча публикуются отчёт и сводка. Сравнение читает
   опубликованные результаты без нового вызова моделей.

Восстановление повторно принимает исходные записи в тот же батч и сохраняет
стрим/состав. После успешного восстановления нужна ручная постановка в очередь.
Удаление стрима удаляет его батчи и историю; frontend требует отдельного подтверждения.

Новые стримы из frontend используют 11 фиксированных критериев, без выбора
чекбоксами. Backend сохраняет поддержку `enabled_criteria` для ранее созданных
снимков и API: отсутствующее поле означает все 11, выбранный набор определяет
`max_total`. Существующие результаты не пересчитываются.

Оценка критерия — 0, 0,5 или 1; критическое нарушение 5.2 — 0 или 1.
По правилу стрима критическое нарушение может обнулить итог, сохранив исходные
баллы. Средние рассчитываются по успешным звонкам; ошибки не заменяются нулём.

Модели, язык и шаблоны ролей/анализа предзаполняются из исходного кода и настроек
при создании стрима и сохраняются в снимке. Frontend показывает редактируемый
промпт Whisper, полученный из backend. Ключи провайдеров не входят в снимок.

База знаний — непустой текст UTF-8, словарь корректировок — JSON-объект строк,
нежелательные выражения — JSON-массив строк. ZIP предназначен для аудиозаписей.
Поле JSON-метаданных в frontend удалено; API-совместимость сохранена, новый способ
передачи метаданных ещё не определён.

## Данные и структура

По умолчанию `data/vox.sqlite3` создаётся при старте. В SQLite хранятся организации,
снимки стримов, батчи, очередь, ошибки приёма, транскрипции и результаты анализа.
Материалы стримов лежат в `data/streams`, входное аудио — в `data/inputs`.
После публикации результатов аудио удаляется механизмом очистки;
транскрипции и результаты остаются в БД. Каталог `data/` не хранится в Git.

| Путь | Назначение |
| --- | --- |
| `backend/api.py` | Маршруты REST, авторизация Bearer-ключом, обработка ошибок |
| `backend/config.py` | Настройки `VOX_*`, пути и ключ команды |
| `backend/database.py` | Схема SQLite, организации и хеши ключей |
| `backend/streams.py` | Создание, валидация материалов и загрузка снимков стримов |
| `backend/archives.py` | ZIP-приём, повтор и восстановление |
| `backend/batches.py` | Батчи, записи, очередь, обработка, отчёты и очистка |
| `backend/worker.py` | Последовательный worker и восстановление прерванной работы |
| `pipeline.py`, `processing_context.py` | Обработка звонка по настройкам снимка |
| `transcriber.py` | Whisper, нормализация и разметка ролей |
| `acoustics.py` | Метрики по тексту и временным границам реплик |
| `analyzer.py`, `checklist.py` | LLM-оценка, критерии и нормализация результата |
| `kb.py`, `config.py` | Чтение базы знаний и исходные настройки обработки |
| `main.py` | Отдельный CLI для анализа одного файла |
| `tests/` | Проверки API, данных и обработки |

Папка `backend/` внутри репозитория — Python-пакет серверного приложения.
Python-файлы в корне также используются: worker вызывает исходный pipeline
с контекстом стрима. `main.py` — отдельный способ запуска, он не нужен для сайта.

## Docker

Для контейнерного запуска используется `Dockerfile` этого репозитория и `compose.yaml` соседнего frontend. API и worker используют один образ с Python, ffprobe и SQLite 3.53.4 и один постоянный том данных. SQLite собирается из официального архива с проверкой SHA3-256; стандартный модуль Python sqlite3 сохраняется. Инструкция: [Docker-развёртывание](../frontend/docs/docker-deployment.md).
